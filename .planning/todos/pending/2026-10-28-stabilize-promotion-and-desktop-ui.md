## Problem

После реализации Phase 14 владелец обнаружил связанный набор регрессий. Их необходимо проверять как цельный пользовательский сценарий, а не как независимые косметические исправления.

### Повышение участника

1. Календарная дата выводится с двойной точкой: русское `г.` получает ещё одну завершающую точку.
2. После показа срока карточки остаются недоступными: нельзя нажать действие и отправить обычный либо квалификационный запрос даже тогда, когда запрос должен быть разрешён.
3. Ник не закрепляется за устройством либо закрепление не восстанавливается при следующем открытии. Нужно проверить cookie, серверный binding, повторный вход и конфликт другого ника.
4. Отправка запросов в целом не проходит. UI обязан различать недоступность по cooldown, активный запрос, ошибку базы, отказ API и успешную отправку, а не просто оставлять кнопку неактивной.

### Редактор заданий и квалификации

5. Нельзя надёжно выбрать количество заданий для звания.
6. Добавление обычного задания и квалификационного вопроса не работает либо не даёт понятного результата сохранения.
7. Кнопки и состояния редактора не соответствуют остальному интерфейсу PORTIA: нужны обычные кнопки проекта, явные disabled/error/saved состояния и рабочий UI на ПК и телефоне.

### Паук, окна и ярлыки

8. Паук сам бесконечно исчезает при выходе из видимой области и появляется заново. Автоматическое исчезновение и relocation запрещены: новое место выбирается только при явном переключении владельцем `Скрыть → Показать`. При обычном движении паук остаётся на паутине и продолжает маршрут. После явного показа стартовая поза не должна каждый раз быть одинаковой.
9. Ограничения перемещения окон асимметричны: окно нельзя нормально увести к левому краю, зато справа можно спрятать больше половины окна за границей рабочего стола.
10. У анимированных ярлыков заметен скачок при переходе к статичному состоянию: меняются качество, масштаб либо геометрия. Последний кадр анимации и статичное изображение должны визуально совпадать.

## Solution

Сначала воспроизвести все пункты на живом локальном сервере и записать сетевые ответы `/api/promotion/status`, `/api/promotion/requests` и `/api/promotion/banks`. Затем исправлять вертикальными срезами с регрессионными тестами:

1. Убрать двойную пунктуацию даты и протестировать русскую локаль.
2. Проследить весь путь eligibility → enabled button → POST → atomic device binding → refreshed projection. Не подменять ошибку базы disabled-состоянием.
3. Проверить реальную Supabase-схему Phase 14 и применённые RPC до изменения клиентского UI.
4. Пересобрать редакторы банка заданий вокруг существующих контролов PORTIA; отдельно проверить выбор количества, добавление, предварительный просмотр и подтверждение.
5. Удалить автоматический lifecycle исчезновения паука; relocation оставить только обработчику пользовательского переключателя, позу рассчитывать от выбранного пути.
6. Исправить clamp окна одним симметричным контрактом для левой и правой границы и покрыть тестами одинаковые допустимые видимые поля.
7. Свести SVG/CSS анимацию ярлыков к тем же viewBox, размерам, фильтрам и геометрии, что и статичный кадр; проверить переход покадрово.

## Acceptance Criteria

- Для доступного участника обе разрешённые заявки отправляются и сразу отражаются в состоянии; для недоступного показана конкретная причина.
- После первой успешной заявки тот же ник восстанавливается на устройстве; другой ник получает безопасный отказ; сброс проверяющим работает отдельно.
- Дата не содержит `..` и не показывает выдуманную точность.
- Редактор выбирает количество, добавляет/изменяет/удаляет задания и вопросы, сохраняет и показывает ошибки без потери введённых данных.
- Паук не исчезает сам; новое место и поза появляются только после ручного `Скрыть → Показать`.
- Окна одинаково ограничены слева и справа, заголовок остаётся доступен.
- Ни один ярлык не меняет резкость, масштаб или положение в момент завершения анимации.
- Сценарии проверены на ПК и телефоне; unit/API/UI тесты и production build проходят.
