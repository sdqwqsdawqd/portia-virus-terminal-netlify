# Phase 14: Приложение «Повышение» - Context

**Gathered:** 2026-10-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Этап реализует целиком отдельное приложение «Повышение»: публичный вход по нику, обычные задания на повышение, отдельные квалификационные проверки, интерфейс проверяющего, сроки, пересдачи, защищённое хранение и очистку. Обычные задания и квалификационные проверки остаются разными процессами. Google-таблица используется только для чтения диапазона `Portia!A61:E85`.

</domain>

<decisions>
## Implementation Decisions

### Доступ участника и привязка устройства

- **D-01:** Обычные задания доступны любому участнику, чей ник находится в `Portia!A61:E85`, если завершён анти-спидран. Квалификационная проверка доступна только участникам со званиями 2, 4 и 6.
- **D-02:** Ник закрепляется за устройством при отправке первой подтверждённой заявки, а не при простом поиске ника.
- **D-03:** Привязка постоянная и снимается только вручную проверяющим. Удаление ника из таблицы не освобождает устройство автоматически.
- **D-04:** Если ник удалён из `Portia!A61:E85`, участник сразу полностью теряет доступ: нельзя смотреть состояние, отправлять заявку, видеть задания или начинать/продолжать тест. Активный процесс можно только закрыть или очистить.
- **D-05:** Попытка использовать другой ник получает нейтральный отказ без раскрытия закреплённого ника.
- **D-06:** Подозрительные повторные попытки получают нарастающее серверное ожидание 5 → 15 → 60 минут. Попытка во время блокировки не перезапускает отсчёт.
- **D-07:** Защита должна сочетать серверную привязку устройства, ограничения по нику/IP и доступные устойчивые признаки клиента. План не должен обещать невозможную стопроцентную защиту после полной очистки данных и смены сети/VPN.

### Работа проверяющего с запросом

- **D-08:** Любой проверяющий с доступом `promo` видит общую очередь и может нажать «Взять запрос».
- **D-09:** Закрепление выполняется атомарно. Только первый успешно взявший запрос получает право менять его; остальные видят занятость.
- **D-10:** Назначенный проверяющий может вернуть запрос в очередь, а владелец — принудительно снять закрепление.
- **D-11:** Закрепление не истекает по короткому таймеру: оно сохраняется до ручного возврата, закрытия либо трёхдневной очистки.
- **D-12:** При отклонении участник видит только нейтральное сообщение «Заявка отклонена» без причины.

### Банки, выдача заданий и сборка теста

- **D-13:** Для каждого целевого звания существует отдельный банк обычных заданий; для переходов Кадет→C, C→B и B→A — отдельные банки квалификационных вопросов.
- **D-14:** Элемент банка можно временно отключить без удаления. Случайная сборка использует только активные элементы, не допускает повторов и блокируется, если элементов недостаточно.
- **D-15:** До подтверждения проверяющий видит полный случайный набор, может пересобрать его или заменить отдельные пункты.
- **D-16:** После подтверждения сохраняется неизменяемая копия набора. Последующее редактирование банка не меняет уже выданные задания или тест.
- **D-17:** Для теста отдельно задаётся количество вопросов каждого типа и порядок. Правильные ответы хранятся только в защищённой части и не отправляются участнику до или во время теста.

### Квалификационная проверка и пересдача

- **D-18:** Проверяющий разрешает тест, и сервер сразу запускает единый лимит 15 минут. Это решение заменяет прежнюю формулировку QUAL-06 про одну минуту на каждый вопрос; движение по вопросам остаётся только вперёд.
- **D-19:** По истечении 15 минут тест закрывается и получает автоматический провал. Уже отправленные ответы сохраняются для проверяющего.
- **D-20:** Проверяющий может вручную отменить автоматический провал по времени или другому техническому событию и принять итоговое решение.
- **D-21:** Любой обрыв соединения во время теста сразу завершает попытку провалом. На ПК уход со вкладки, потеря фокуса и выход со страницы также завершают её провалом; ранее отправленные ответы сохраняются.
- **D-22:** Любой проверяющий с доступом `promo` может досрочно снять ожидание пересдачи. Действие сохраняется в краткой истории.
- **D-23:** Базовый срок пересдачи остаётся 2 дня, проверяющий может изменить или увеличить его; число попыток не ограничено.

### the agent's Discretion

- Детальная компоновка карточек банков и preview при сохранении обозначенных правил.
- Конкретный состав устойчивых сигналов устройства и формула риска в пределах приватности браузера и доступной серверной инфраструктуры.
- Техническое разбиение API и таблиц при сохранении раздельных state machine для заданий и квалификационных проверок.

## Existing Code Insights

### Reusable Assets

- `components/portia-desktop.tsx`: оконная модель рабочего стола и неблокирующее уведомление `QuestToast`, которое задаёт визуальный образ уведомления о доступной пересдаче.
- `components/portia-editor.tsx`: существующие вкладки редактора, формы, сворачиваемые карточки и управление trusted-вкладками.
- `lib/editor-access.ts`: серверная проверка прав редактора; все операции проверяющего должны требовать доступ `promo`.
- `lib/request-json.ts`: единая безопасная обработка JSON для новых API.
- `lib/portia-employees.ts`: существующий пример чтения и нормализации внешнего CSV, но новый диапазон повышения нельзя смешивать с приложением «Сотрудники».
- `supabase/portia_setup.sql`: подготовленная модель `closed_tabs`/`granted_tabs`, RLS и trusted-вкладок.

### Established Patterns

- Критичные права проверяются и в route handler, и в Supabase/RLS; клиентские проверки не считаются защитой.
- Публичные и редакторские маршруты разделяются, приватные ответы используют `no-store`.
- Внешние данные нормализуются на границе; Google-таблица остаётся read-only источником истины для текущего звания.
- Интерфейс использует React state без отдельной state-библиотеки; серверные timestamps являются источником истины для сроков.

### Integration Points

- Новый ярлык и окно подключаются к реестру приложений и окон в `components/portia-desktop.tsx`.
- Ветка `promo` подключается к редактору и системе выдачи trusted-доступов в `components/portia-editor.tsx` и `/api/access`.
- Новые публичные и проверяющие API размещаются под `app/api/`, используя Supabase server clients и проверку `promo`.
- Новые таблицы, RPC и RLS добавляются идемпотентно в `supabase/portia_setup.sql`.

<specifics>
## Specific Ideas

- Участник не создаёт аккаунт: идентификация начинается с ника из таблицы, но первая заявка закрепляет ник за устройством.
- Защита от параллельной работы проверяющих должна быть не визуальной блокировкой, а атомарной серверной операцией.
- Тест использует один общий 15-минутный таймер, а не отдельную минуту на каждый вопрос.
- Автоматический провал является начальным системным результатом, который уполномоченный проверяющий может отменить вручную.

</specifics>
