<user_constraints>
## User Constraints (from CONTEXT.md)

### Locked Decisions

- Ordinary promotion tasks and qualification tests are separate state machines.
- Only nicknames currently present in `Portia!A61:E85` have access. Removal revokes access immediately.
- Ordinary tasks are available after anti-speedrun; qualification is available only at titles 2, 4, and 6.
- The first confirmed request permanently binds the nickname to the device until a reviewer resets it.
- Suspicious attempts use progressive waits of 5, 15, and 60 minutes and never reveal the bound nickname.
- A reviewer explicitly and atomically claims a request; only the assignee may mutate it, while the owner may force-release it.
- Banks are separate by target title or qualification transition; confirmed assignments/tests store immutable snapshots.
- Qualification uses one server-authoritative 15-minute limit, forward-only questions, immediate technical-failure status, and reviewer override.
- Any connection loss fails the attempt. Desktop focus/visibility/page exit also fails it; phone skips focus protection.
- Any `promo` reviewer may release a retake early, and the action is retained in compact history.

### the agent's Discretion

- UI composition for banks and preview.
- Practical device-risk signals that respect browser limits.
- Exact API/table decomposition while preserving separate workflows.

### Deferred Ideas (OUT OF SCOPE)

- External reviewer notifications, analytics, and a generalized application framework.

<research_summary>
## Summary

No new runtime dependency is required. The existing Next.js route-handler + Supabase RPC pattern is sufficient, but the workflow must not be implemented as a large JSON payload or client-controlled state. Use normalized promotion tables, explicit status columns, database constraints, and narrowly granted RPCs for every transition that must be atomic: binding a device, submitting a request, claiming it, confirming an immutable assignment, starting/failing a test, closing a result, and pruning history.

The anonymous participant should receive an opaque HttpOnly device credential generated by the server. Store only its hash in Postgres and combine it with coarse, keyed server-side risk signals and nickname/IP attempt buckets. This raises abuse cost but cannot guarantee identity after a full storage wipe plus network/browser change. Do not expose raw fingerprints, bound nicknames, answer keys, future questions, reviewer identity, or internal notes.

The 15-minute qualification attempt is a database state machine. The start RPC writes `started_at` and `deadline_at`; every answer submission rechecks `now() < deadline_at` and current sheet membership. Visibility/focus/offline events send an idempotent failure transition, while every subsequent request also reconciles expired attempts so correctness never depends on `beforeunload` or a browser timer.

**Primary recommendation:** implement a server-authoritative, RPC-driven workflow with immutable snapshots and safe public projections; keep the existing React/Next/Supabase stack unchanged.
</research_summary>

### Pattern 1: Atomic conditional transition

Use one SQL function/statement whose `WHERE` clause includes the expected status and assignment state, then return the changed row. A zero-row result means the request was already claimed or state changed. Never perform “read available → update claimed” as separate client calls.

### Pattern 2: Safe public projection

Public routes select or construct explicit fields only. Keep answer keys, reviewer IDs, internal notes and future questions in tables without direct anon grants. The browser gets one current question only after the server commits the previous answer.

### Pattern 3: Idempotent failure and deadline reconciliation

`fail_attempt(attempt_id, reason)` should be safe to call repeatedly. Every test read/answer checks the stored deadline and transitions expired attempts before returning. Client events improve speed of detection but are never the sole enforcement path.

### Pattern 4: Snapshot at confirmation

Bank rows are mutable configuration; issuance copies the chosen text/options/type/order into immutable assignment/test snapshot rows. Bank edits cannot alter an active participant experience or audit result.

### Anti-Patterns to Avoid

- Direct anonymous table access to workflow tables.
- Storing answer keys beside public question payloads and filtering only in React.
- Trusting device time, a JavaScript interval, `beforeunload`, IP alone, or a raw fingerprint.
- Treating Google Sheet outages as “not found”; return temporary unavailable and write nothing.
- Multiple cross-table mutations from route code without one database transaction.
</architecture_patterns>

<dont_hand_roll>
## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Atomic claim/state transitions | Client-side lock flags | Postgres RPC with conditional update/transaction | Eliminates reviewer races. |
| Deadline enforcement | Browser countdown as truth | `deadline_at` + database `now()` | Background throttling and clock changes cannot bypass it. |
| Cleanup scheduler | Visitor-triggered cleanup only | Supabase Cron + idempotent SQL function | Works during zero traffic. |
| Authorization | Hidden buttons | route check + grants/RLS/RPC privilege | Direct requests remain protected. |
| Device identity | Stable hardware fingerprint promise | opaque HttpOnly credential + risk signals + reviewer reset | Browser privacy controls intentionally prevent perfect identity. |

**Key insight:** the hard parts are concurrency and trust boundaries, not UI state. Put irreversible transitions in Postgres and make the UI a projection of server state.
</dont_hand_roll>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: Two reviewers claim the same request
**Avoidance:** conditional RPC transition with one winner and a concurrency test.
**Warning sign:** route first fetches `status = pending`, then issues a separate update.

### Pitfall 2: Public data leaks the test bank
**Avoidance:** explicit response DTOs, no anon table grants, endpoint contract tests that search for answer/future-question/internal fields.
**Warning sign:** route returns a database row with `select('*')`.

### Pitfall 3: Device protection locks legitimate users forever
**Avoidance:** owner/reviewer reset flow, neutral error, hashed token, documented limits, and table-removal fail-closed handling.
**Warning sign:** no recovery operation exists or raw device token is stored.

### Pitfall 4: Network errors become false “nickname missing” results
**Avoidance:** distinguish `not-found` from `sheet-unavailable`; never create/close records when eligibility cannot be rechecked.
**Warning sign:** catch block returns an empty roster.

### Pitfall 5: Timer passes because the tab slept
**Avoidance:** server deadline checks on every action and on reviewer/public reads; client countdown derives from deadline.
**Warning sign:** result depends on `setTimeout(15 * 60 * 1000)` firing.

### Pitfall 6: Cleanup deletes active or auditable state
**Avoidance:** statuses and timestamps define exact cleanup candidates; close transaction writes compact result before deleting payload; retain only newest three results per nickname.
**Warning sign:** broad `updated_at < now()-3 days` delete without status predicates.
</common_pitfalls>

## Code Examples

### Secure database function boundary

```sql
-- Based on Supabase database-function security guidance.
create or replace function public.portia_promo_claim(target uuid)
returns uuid
language plpgsql
security definer
set search_path = ''
as $$
declare claimed uuid;
begin
  if not public.portia_has_tab_grant('promo') then
    raise exception 'forbidden';
  end if;
  update public.portia_promo_requests
     set reviewer_id = auth.uid(), status = 'claimed', updated_at = now()
   where id = target and status = 'pending' and reviewer_id is null
   returning id into claimed;
  return claimed;
end $$;
revoke execute on function public.portia_promo_claim(uuid) from public, anon;
grant execute on function public.portia_promo_claim(uuid) to authenticated;
```

<open_questions>
## Open Questions (RESOLVED)

1. **Can Supabase Cron be enabled in the production project?**
   - **RESOLVED:** Keep cleanup idempotent and callable from the reviewer path; the owner-run SQL checkpoint verifies/enables the scheduled job where the production project supports it. A missing schedule never authorizes unsafe cleanup during a Sheet outage.

2. **How should a test distinguish phone from desktop?**
   - **RESOLVED:** Derive mode once at attempt creation from viewport/input/user-agent signals, classify ambiguous devices as desktop, store the result in the server attempt snapshot and prohibit later mutation. Spoofing remains a documented residual risk rather than a promised security boundary.

3. **How is IP obtained consistently on Netlify?**
   - **RESOLVED:** Use the existing server-only trusted forwarded-header extractor, normalize the selected address into a coarse keyed risk bucket, reject malformed chains and never persist or return raw IP. Representative Netlify header fixtures remain required in the API tests.
