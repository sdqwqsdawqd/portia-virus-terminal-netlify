# Phase 03.1 Plan 01: Editor stabilization Summary

СОХРАНИТЬ now stays reachable with the format panel open. The bar stays mounted while the panel is open. On desktop the panel sits 72px above the window's bottom, absolute in the editor window. On the phone it sits above the bar, which sits above the taskbar. A colour click applies exactly the clicked colour, because the panel no longer moves under the pointer and its readouts come from the document. The employee list scrolls in its own column. The access tab can no longer hang in «Загрузка списка…» or with ВЫДАТЬ ДОСТУП disabled.

## D-02 mechanism (Task 1 Step 1)

Confirmed by code trace: **candidate (b)**. It was not reproduced in a live browser (that needs the owner's login).
- Trace: swatch onClick -> applyStyle -> commit -> target.onCommit (changeFormattedText -> draft becomes dirty) + onUpdate({...target, document}). The first edit makes `dirty` true, so `barVisible` mounts `.editor-savebar`. The old desktop rule `.content-editor:has(> .editor-savebar) .floating-text-format { bottom: 76px }` then lifted the panel from 50px to 76px. The panel's contents moved 26px up under a pointer that had not moved. Swatches are 30px with a 5px gap, and the 8 text swatches wrap inside a half-width card. The next click at the same spot therefore landed about one row lower, on another swatch or control. That is the owner's "перебирает цвета". If the status text wraps to two lines (for example «СОХРАНЕНИЕ…» plus the section list), the bar gets taller and the panel can move again.
- (a) Not the cause of the cycling. onUpdate keeps the same selection, so the key `key:start:end:surface` stays the same and a swatch click does not remount the panel. (a) only re-seeded the readouts after a selection change, which was correct but fragile. Removed anyway.
- (c) Not the cause. `commit` sets `documentRef.current` synchronously before the next click, and target.document equals the committed document after onUpdate.
- All three were removed, as the plan says: the bar is mounted while the panel is open, the panel offset is constant, the bar stays one line, the panel is keyed by the field and its style is derived.

## Deviations from Plan

**1. [Rule 1 - Bug] Selector specificity raised for two CSS rules**
- **Found during:** Tasks 1 and 2
- **Issue:** The new desktop rules sit in the `@media (min-width: 901px)` block at about line 421. That block comes before the base `.floating-text-format { position: fixed; bottom: 50px; … }` rule (about line 531) and the base `.virus-editor-layout { align-items: start }` rule (about line 435). With plain `.floating-text-format` / `.employee-editor-layout` selectors, the later base rules would win and the fix would do nothing.
- **Fix:** I used `.content-editor > .floating-text-format` and `.virus-editor-layout.employee-editor-layout`. The other rules already had higher specificity.
- **Commits:** 17c9347, d32f105

**2. [Rule 2] Phone panel offset changed in place**
- The plan asked for an added rule `.content-editor:has(.floating-text-format) .floating-text-format { bottom: 100px }`. I changed `bottom: 44px` to `bottom: 100px` in the existing phone `.floating-text-format` rule instead. The panel is always inside `.content-editor`, so the effect is the same with one rule fewer.

**3. Bar text forced to `display: flex` on the phone while the panel is open**
- The phone bar's `<p>` is `display: block` with block spans, so it would stack status and sections onto two lines. Adding `display: flex` to the one-line rule keeps it on one line at every width, as rule 6 intends.

## Known limits

- The desktop panel's `bottom: 72px` assumes the one-line bar is about 58px tall. If the bar's font or padding changes later, the offset must change with it.
- Phone: the 34svh panel cap, the 56px bar and the 44px taskbar together leave less room for text on very short screens (landscape). This has not been checked on a device.
