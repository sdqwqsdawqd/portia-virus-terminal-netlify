Root causes found by reading at planning time (line numbers are planning-time; re-grep the anchors before editing):

D-01. On desktop, `.floating-text-format` (app/portia.css ~527) is `position: fixed; right: 14px; bottom: 50px`. The
editor window has `transform: none` once it has geometry (createWindowGeometry gives every desktop window geometry at
open), so the panel is placed against the browser viewport. The save bar `.editor-savebar` (~407) is `position: sticky;
bottom: 0` inside the scrolling `.content-editor`, which puts it at the bottom of the editor window. The lift rule
`@media (min-width: 901px) { .content-editor:has(> .editor-savebar) .floating-text-format { bottom: 76px; } }` (~421)
works only when the window's bottom edge is the viewport's bottom edge. Even maximized, the window ends at viewport − 52px
(44px taskbar + 8px inset) and the bar is about 58px tall, so it spans viewport −110…−52. A panel ending at viewport −76
covers its upper half, including the right-hand СОХРАНИТЬ. This matches the owner's screenshot. A window placed higher
up gets covered anywhere.
On phones (900px block ~1028-1038) the panel is fixed at `bottom: 44px` where the bar is, and the rule
`.content-editor:has(.floating-text-format) .editor-savebar` hides the bar while the panel is open. SC1 requires СОХРАНИТЬ
on the phone with the panel open, so on the phone this hiding is the cause and changes. CONTEXT D-01: "stays unless it is
the cause".

D-02. The cause is not certain from reading. Candidates, all in components/portia-editor.tsx:
 (a) The panel element is keyed by `${formatTarget.key}:${selection.start}:${selection.end}:${previewSurface}` (~1178), so
     every selection change remounts it. Its colour, size, weight and background are local useState values seeded once
     from `richTextStyleAt(target.document, target.selection.start)` at mount (~1546-1554). After a remount the readout
     and the ✓ swatch can show a different colour than the one just applied. .planning/debug/format-panel-select-closes.md
     already observed this re-seeding.
 (b) The panel moves under the pointer. The first click makes the draft dirty, the bar mounts
     (`barVisible = dirty || …`, ~844), and the desktop lift rule moves the panel from bottom 50px to 76px. On phones the
     bar would mount under the panel. The next click at the same spot then hits a different control or swatch.
 (c) documentRef is synced from target.document in an effect (~1556). A re-seeded or stale target can make the next
     applyStyle start from another document.
The fix removes all three sources: a stable panel position (bar always mounted while the panel is open, constant offset,
one-line bar), no remount on selection change, and no local copy of the style. Step 1 of Task 1 confirms which candidate
it was, and that goes in the SUMMARY.

D-04. `.editor-record-list` (~432) is `position: sticky; top: 0; display: grid` with no height bound or overflow. With the
full roster (dozens of employees) the column is taller than the editor's scrollport, so the whole `.content-editor`
scrolls. `.content-editor` (~399) is a flex column with a definite height (`calc(100% - 46px)`), and every child has
`flex-shrink: 0` (~400).

D-09 #9. EditorAccessManager (~1720-1775): loadEditors, addEditor and removeEditor await fetch and response.json() with
no try/catch. A network error, a hung request or an HTML error page leaves `state` at "loading" or "saving" and raises an
unhandled rejection.

Baselines: npm test 85 passing; npm run lint 0 errors / 13 no-img-element warnings.
