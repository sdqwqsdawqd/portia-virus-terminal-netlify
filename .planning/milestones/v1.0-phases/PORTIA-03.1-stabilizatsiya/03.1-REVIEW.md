# Phase PORTIA-03.1: Code Review Report

**Reviewed:** 2026-10-18
**Depth:** standard
**Files Reviewed:** 21
**Status:** issues_found

## Summary

Scope was resolved through the degraded phase-directory range, so it includes phase 03.2 work in the same files. Files were reviewed as they stand now. For cross-file claims I also read `lib/editor-history.ts`, `lib/content-sync.ts`, `lib/portia-cdn.ts`, `lib/editor-access.ts` and `app/api/content/route.ts`. No structural (fallow) findings were supplied.

No BLOCKER-class defect was proven. The pure-logic modules are sound: `broadcasts.ts`, `window-geometry.ts`, `editor-items.ts` and the `editor-changes.ts` section mapping behave as their tests say. The risk is concentrated in three places:

- **Sync glue.** The desktop poll, the employee roster cache and the editor history interact in ways that quietly drop data or history (WR-01, WR-04).
- **Server-side normalization and sanitization.** Both are more permissive or more lossy than their comments claim (WR-02, WR-07).
- **Save path.** It is coupled to third-party availability (WR-03).

The most important items to fix are WR-01, WR-02, WR-04 and WR-07.

## Warnings

### WR-01: A degraded roster replaces good profile data on screen and in the localStorage cache

**File:** `components/portia-desktop.tsx:404-419` (with `lib/portia-employees.ts:70-73`)
**Issue:** When the Supabase profile read fails, `/api/employees` answers 200 with `degraded: true` and `profilesRead: false`. Every employee then carries `emptyProfile`: biography `""`, all ratings `null`, photo `""`.

`acceptsRoster` accepts any non-empty degraded roster. `fetchEmployees` therefore calls `setEmployees(payload.employees)` and writes the payload to `employeesCacheStorageKey`. For up to the next poll (5 minutes) every visitor sees "Биография … не заполнена" and "—" for all ratings. The cached copy that would have survived an outage is overwritten with the blank one.

The comment on `acceptsRoster` says a partial sync must not wipe the list, but it wipes the content of the list. The editor side already has the matching guard (`profilesRead === false` is rejected), so the reader side is inconsistent with it.

**Fix:**
```ts
// fetchEmployees, after acceptsRoster(payload):
const profilesLost = (payload as { profilesRead?: boolean }).profilesRead === false;
if (profilesLost && employeesRef.current.length) {
  // keep the stored profile fields, take only roster and avatar data from the degraded answer
  setEmployees((current) => payload.employees.map((fresh) => {
    const old = current.find((employee) => employee.id === fresh.id);
    return old ? { ...fresh, biography: old.biography, photoUrl: old.photoUrl, knowledgeRating: old.knowledgeRating,
      pawsRating: old.pawsRating, bioRating: old.bioRating, sRating: old.sRating,
      activityRating: old.activityRating, testsRating: old.testsRating, overallRating: old.overallRating } : fresh;
  }));
  return; // and do not write the degraded payload to the cache
}
```

### WR-02: PATCH is a full replace for biography and photo; a missing or mistyped field erases the stored value

**File:** `lib/portia-employees.ts:296-303` (called from `app/api/employees/route.ts:35`)
**Issue:** `sanitizeEmployeeUpdate` turns a missing or non-string `biography` into `""` and a missing or non-string `photoUrl` into `""`. `saveEmployeeProfile` then upserts those values. The ratings in the same function are treated as "missing = unchanged" (documented on `EmployeeUpdate`), so the contract is inconsistent.

Any caller that sends `{ id, changes: { bioRating: 5 } }`, or a client bug that drops the field, silently wipes the stored biography and photo. The UI-side guard ("Blank profiles must not become drafts") does not protect the API. `portia-employees.test.ts` has no test for an update without `biography`.

**Fix:**
```ts
if (typeof candidate.biography !== "string" || typeof candidate.photoUrl !== "string") return null; // route answers 400
const photoUrl = candidate.photoUrl.trim().slice(0, 2048);
```
Add a test that `sanitizeEmployeeUpdate({ pawsRating: 5 })` returns `null`.

### WR-03: Saving a profile depends on live Google Sheets and Roblox availability and can answer 404 for a valid employee

**File:** `app/api/employees/route.ts:37-40`, `lib/portia-employees.ts:249-270`
**Issue:** PATCH calls `loadEmployees()`, which fetches the sheet and then the Roblox users and thumbnails endpoints, just to locate the employee by id. The ids are derived from the Roblox lookup.

For an employee who has no stored `roblox-N` row yet, a Roblox outage makes the server compute `nick-…` while the client sends `roblox-N`. `employees.find` then fails and the editor gets "Сотрудник не найден. Обновите страницу." for a valid employee. The client cannot fix this by refreshing during the outage.

The worst-case latency also stacks: sheet 8 s in parallel with the profile read, then Roblox 5 s, then thumbnails 5 s, about 18 s. That exceeds the default serverless limit, so the save can time out for a reason unrelated to the database.

**Fix:** For PATCH, resolve the employee from the sheet only and accept the client's `id` if it matches `roblox-\d+` or `employeeId(nickname, null)` for a sheet row. This needs no Roblox call. Alternatively, skip `resolveRobloxProfiles` in PATCH and match on either id form.

### WR-04: Every poll replaces the content object, so the editor's clean-state sync wipes undo/redo history

**File:** `components/portia-desktop.tsx:358-362`, `components/portia-editor.tsx:586-594`, `lib/editor-history.ts` (`sync` case)
**Issue:** `fetchContent` calls `setContent(fetched)` with a fresh object every 10 s, even when `fetchedRevision === knownRevision.current`. `acceptFetchedContent` deliberately accepts an equal revision.

The editor's sync effect fires when `dirty` becomes false. The reducer's `sync` is a no-op only if `action.content === state.source`, and after any poll that is never true. So the typical flow is: edit for more than 10 s (a poll lands while dirty), then press «ВЕРНУТЬСЯ СОХРАНЁННОЕ» or undo back to clean. The effect then runs `initHistory` and discards `past` and `future`.

This breaks the documented contract in the reducer ("undo can bring the edits back" after `discard`) and drops the redo stack after undoing to clean. The same needless identity change also re-runs every `content`-keyed effect (broadcast signature, quest toast recompute, `rememberActiveQuests` localStorage write) every 10 s.

**Fix:**
```ts
// fetchContent
if (fetchedRevision === knownRevision.current) return; // nothing new: keep the current object
```
This must be done after the stale-answer guard and must still reach `finally`. Optionally also compare `revision` inside the editor sync effect instead of object identity.

### WR-05: EmployeeImage keeps `failed`/`loaded` after `src` changes

**File:** `components/portia-desktop.tsx:1334-1343`
**Issue:** `failed` and `loaded` are never reset when `src` changes. The parent `key={selectedEmployee.id}` only remounts when the selected employee changes. The editor flow is: a photo URL is broken, the visitor view shows the fallback logo (`failed = true`), the editor fixes the URL, and `updateEmployee` swaps `photoUrl`. The new URL is never tried, because `fallback = !src || failed` stays true. The profile keeps showing the logo until another employee is selected or the page reloads.

**Fix:** Add `key={src}` on `<EmployeeImage>` at both call sites, or reset state when `src` changes:
```tsx
return <EmployeeImageInner key={src} src={src} alt={alt} fallbackClassName={fallbackClassName} />;
```

### WR-06: The employee editor's «СОХРАНЕНО» timer is never cleared

**File:** `components/portia-editor.tsx:1426`
**Issue:** `window.setTimeout(() => setState("idle"), 1800)` is unguarded. A second save started within 1.8 s of the first is flipped to `idle` mid-request. The button is re-enabled and `chooseEmployee` (guarded by `state !== "saving"`) allows switching employee while a PATCH is in flight. That PATCH's answer then overwrites the next employee's draft, which is the scenario the comment at line 1452 says it prevents. The desktop's `saveStateTimer` handles exactly this; the employee editor lacks the equivalent.

**Fix:**
```ts
const savedTimer = useRef<number | null>(null);
// in save(): if (savedTimer.current) clearTimeout(savedTimer.current); before setState("saving")
savedTimer.current = window.setTimeout(() => setState("idle"), 1800);
// and clear it in an unmount effect
```

### WR-07: `normalizePortiaContent` silently truncates rich text and passes item shapes through unvalidated

**File:** `lib/portia-content-normalize.ts:43, 64, 83-94, 176`
**Issue:**
- A rich-text document is cut to the first 500 runs (line 43). `formattedText` keeps only the first 1000 keys (line 64). A run is created per style change, so a heavily formatted field can exceed 500 runs. The reader then renders truncated text while the plain `text` field still holds the whole string.
- Because `PUT /api/content` does not reject, the owner sees "saved" and loses the tail of the text or the newest formatting. After the next poll the editor shows the truncated server copy.
- The header comment claims "unknown input in, a complete PortiaContent out", but `infoSections` is passed straight through (line 176). `normalizeBroadcasts` spreads `...item` and does not check `id`, `title`, `body` or `published`. Viruses spread `...virus` without checking `classification`.
- A payload with, for example, `title: {}` is stored and then crashes every visitor's render with "Objects are not valid as a React child". There is no error boundary. This needs an editor-level or client bug, not an anonymous attacker.

**Fix:** Either reject over-limit input in `PUT` with 400 and an editor message, or raise and document the limits. Coerce string fields explicitly in `normalizeBroadcasts` and for `infoSections`:
```ts
.map((item) => ({ ...item, id: String(item.id ?? ""), title: str(item.title), body: str(item.body), published: item.published === true, ... }))
```
Also filter out items without a non-empty string `id`.

### WR-08: Permanent deletes leave orphan `formattedText` keys, contradicting the phase invariant

**File:** `components/portia-editor.tsx:663-669` and `1185-1190` (compare `lib/editor-items.ts:14-23`)
**Issue:** `removeBroadcast` and `removeInfoSection` delete the item's `formattedText` key ("no orphan text stays in formattedText"). `deleteSelectedRecycledVirus` does not remove `virus:<id>:*`, including mutation keys. Deleting a recycle file does not remove `recycle:<id>:content`.

Orphans are persisted and count toward the 1000-key cap in WR-07. They also make `changedSections` classify stray `virus:` keys as the "recycle" section. The formatting of a hard-deleted virus is never garbage-collected.

**Fix:** Add `removeRecycledVirus(content, id)` and `removeRecycleFile(content, id)` to `editor-items.ts`. They should delete every `formattedText` key starting with `virus:${id}:` or equal to `portiaTextKey.recycle(id)`. Add tests next to the existing `removeBroadcast` tests.

### WR-09: A news item's hidden `important` flag survives a type change and shows «ВАЖНО» on quests with no way to clear it

**File:** `components/portia-editor.tsx:1061-1069, 1080`, `components/portia-desktop.tsx:1220`
**Issue:** The «Важная новость» checkbox renders only for `type === "news"`. Changing the type of an important news item to quest or task keeps `important: true`. The reader card renders `· ВАЖНО` and the `.important` styling for any type, so the quest is permanently highlighted. The editor offers no control to clear it except switching the type back.

**Fix:** Clear it in the type handler: `item.type = type; if (type !== "news") item.important = false;`. Optionally also gate the reader on `item.type === "news" && item.important`.

### WR-10: Assistant tip text can be `undefined` and crashes the whole desktop

**File:** `components/portia-desktop.tsx:1089-1091` (renders into `FormattedText`, line 1734-1736)
**Issue:** `content.assistantAdvice[assistantTipIndex]` has no fallback, unlike the offended, idle and activity branches. If a 10-second sync shortens the advice list while the bubble is visible (5.2 s window), the index is out of range. `FormattedText` then builds `runs = [{ text: undefined }]` and `run.text.length` throws a TypeError. There is no error boundary, so the entire desktop unmounts for visitors.

**Fix:**
```ts
? (content.assistantAdvice[assistantTipIndex] ?? "Добавьте советы в редакторе PORTIA.")
```
Also add a `text ?? ""` guard inside `FormattedText`.

### WR-11: Editor access trusts the JWT email while an anonymous oracle confirms which emails are approved

**File:** `supabase/portia_setup.sql:52-97`
**Issue:**
- `portia_is_owner` and `portia_can_edit` authorize on `auth.jwt() ->> 'email'` only, with no check that the address is confirmed.
- `portia_editor_is_approved(text)` is executable by `anon`. Anyone can test whether a given address is the owner or an approved editor.
- If the Supabase project has "Confirm email" disabled, an attacker can sign up with an approved editor's address before that person does. The attacker then gets a session and `portia_can_edit()` returns true. Editors can write the public site content.
- This depends on dashboard configuration that is not visible in the repo.

**Fix:** Require a confirmed address in the helpers, for example by joining `auth.users` on `auth.uid()` with `email_confirmed_at is not null`. Document "Confirm email must stay on" next to the setup script. Prefer a sign-up hook over a public RPC, or at minimum rate-limit it. Do not expose a yes/no answer for arbitrary emails to `anon`.

### WR-12: `changedDossierTabs` spreads a possibly missing `recycledViruses`

**File:** `lib/editor-changes.ts:76`
**Issue:** `[...content.viruses, ...content.recycledViruses]` throws if the field is absent. Cached content from before the field existed is accepted by `isUsableContent`, which does not require it. The rest of the editor and the desktop treat the field as optional (`?? []` at `portia-desktop.tsx:933`, `portia-editor.tsx:130`). A render-time throw inside the editor happens when an editor opens the dossier tab on such a cached copy while offline.

**Fix:** `[...content.viruses, ...(content.recycledViruses ?? [])]`.

## Info

### IN-01: Settings storage key is a bare literal in three places and the boot test cannot detect drift

**File:** `lib/accent-boot.ts:10`, `components/portia-desktop.tsx:528, 669`
**Issue:** `"portia-desktop-settings-v1"` is repeated. `accent-theme.test.ts` feeds `getItem` a function that ignores the key, so a rename in one place leaves the boot script reading nothing while all tests stay green.
**Fix:** Export `settingsStorageKey` from `accent-boot.ts`, interpolate it into the script via `JSON.stringify`, import it in the desktop, and assert the requested key in the test.

### IN-02: `startsWith("/")` accepts protocol-relative URLs

**File:** `lib/portia-employees.ts:297`, `lib/portia-content-normalize.ts:76`, `components/portia-editor.tsx:61`, `supabase/portia_setup.sql:22`
**Issue:** `//host/x.png` passes as a "local path" and resolves to an arbitrary host in the visitor's scheme. Off-site `https://` is allowed anyway, so this is a validation inaccuracy rather than a bypass.
**Fix:** Use `/^\/(?!\/)/` in the three TypeScript checks and `like '/%' and photo_url not like '//%'` in the SQL.

### IN-03: `staffRowsEnd = 35` silently drops staff beyond 34

**File:** `lib/portia-employees.ts:84`
**Issue:** Rows after the 34th are ignored with no log or signal. The comment says rows 36+ hold totals, but nothing detects a 35th employee.
**Fix:** Stop at the first row whose number column is empty or at a "Сотрудников:" label instead of a fixed count, or `console.warn` when a populated nickname appears right at the boundary.

### IN-04: Accessibility mismatches

**File:** `components/portia-desktop.tsx:1132, 1715`
**Issue:**
- `QuestToast` handles Escape on the `aside`, but the toast never receives focus, so Escape works only after the visitor tabs into it.
- It uses `role="status"` while containing buttons.
- The virus list has `role="listbox"` with `<button>` children and no `option` roles, which violates the required-children rule.

**Fix:** Listen for Escape on `window` while the toast is shown, use `role="region"` plus `aria-label`, and either drop the `listbox` role or give rows `role="option"` and `aria-selected`.

### IN-05: Unprofessional and empty user-facing strings in the editor

**File:** `components/portia-editor.tsx:1656, 1700, 1244`
**Issue:** The hint «…не добавляй всякой фигни ок?», the guidance «дружок пирожок» and an empty `<small></small>` ship in the editor UI.
**Fix:** Replace with neutral copy and remove the empty element.

### IN-06: Malformed or `null` JSON body gives 500 instead of 400

**File:** `app/api/employees/route.ts:33-34`
**Issue:** `await request.json()` throws on invalid JSON, and `null` makes `body.id` throw. Both fall into the generic catch, log an error and return 500 «Не удалось сохранить профиль».
**Fix:** Parse in a small try/catch, check `body && typeof body === "object"`, and return 400.

### IN-07: Embedded third-party documents have no `sandbox`

**File:** `components/portia-desktop.tsx:1479`
**Issue:** The charter iframe loads a personal GitHub Pages site without the `sandbox` attribute. That page can navigate the top window after a user gesture, run popups and so on.
**Fix:** `sandbox="allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox"` (Google's viewer needs `allow-same-origin`/`allow-scripts`), without `allow-top-navigation`.

### IN-08: Quest period is not validated (end before start)

**File:** `components/portia-editor.tsx:1074-1075`, `lib/portia-content-normalize.ts:79-80`
**Issue:** Only the date input's `min` attribute stops `endsAt < startsAt`, and typing bypasses it. Such a quest is never active: "upcoming" before the start day, "finished" after it. It never pops up, and the editor gets no feedback.
**Fix:** In `normalizeBroadcasts`, clear `endsAt` (or swap) when `endsAt < startsAt`, and show a hint in the editor.

### IN-09: Side effects inside React state updaters

**File:** `components/portia-desktop.tsx:393-402, 703-710`
**Issue:** `updateEmployee` writes localStorage inside the `setEmployees` updater, and `focusApp` calls `setWindows` inside the `setTopZ` updater. Updaters must be pure. They are re-invoked in Strict Mode and under concurrent rendering. It works today only because both are idempotent.
**Fix:** Compute `next` from a ref or derive the cache write in an effect keyed on `employees`; keep a z counter in a ref.

### IN-10: Public tables expose internal columns, and the owner address is committed

**File:** `supabase/portia_setup.sql:49, 155-162, 192-196`
**Issue:**
- `select` is granted to `anon` on the whole of `portia_employee_profiles` (`using (true)`), so `updated_by` (an `auth.users` UUID) and `nickname` are readable through the REST API.
- The owner's personal email is hard-coded in the committed script.
- The storage `select` policy lets anonymous clients list every object in `portia-media`, although a public bucket needs no policy for direct URLs.

**Fix:** Expose the public data through a view or column-level grants that omit `updated_by`. Drop the storage `select` policy if listing is not needed. Keep the owner email in a deploy-time setting.
