# Phase 03.3: Code Review Report

## Summary

Reviewed the manual-employee API (POST/DELETE/PATCH details), the roster merge, the guide tree (subsections and text/table/photo/video blocks), the normalizer, the editor and desktop UI, the SQL table, and the CSS. `tsc --noEmit` is clean and `npm test` passes (152/152).

Access control is sound: every mutating handler checks `getEditorAccess`, and the table has RLS with column-scoped UPDATE. YouTube ids are validated twice, in `parseYoutubeId` and again by regex in `normalizeInfoBlock`, so the iframe `src` cannot take attacker-controlled text. The 4 warnings are silent data loss and transient-failure behaviour, not exploitable holes.

## Warnings

### WR-01: Server normalizer silently truncates guide content the editor lets you create

**File:** `lib/portia-content-normalize.ts:140,155,170`
**Issue:** `normalizeInfoSections` caps subsections at 50, blocks per subsection at 100, and table rows at 100 with `.slice(...)`. The editor (`components/portia-editor.tsx` around lines 1050-1100) has no matching limit: the "+ ПОДРАЗДЕЛ", "+ ТЕКСТ", "+ СТРОКА" etc. buttons add without bound. `/api/content` PUT runs `normalizePortiaContent`, so item 51, 101 or the 101st table row is dropped on save and the editor gets no signal. The draft still shows the dropped items until the next reload, after which they are gone. That is silent data loss, and a 100-row table is a realistic guide.
**Fix:** Either raise the caps well above realistic use, or enforce the same constants in the editor (disable the add buttons at the limit) and share them from `lib/portia-content.ts`:
```ts
export const infoLimits = { subsections: 50, blocks: 100, tableRows: 100 } as const;
// editor: disabled={subsection.blocks.length >= infoLimits.blocks}
// normalizer: .slice(0, infoLimits.blocks)
```

### WR-02: A failed manual-employee read removes them from every device and overwrites the cache

**File:** `lib/portia-employees.ts:312-326,368-376` (consumer `components/portia-desktop.tsx:422-426`)
**Issue:** If `readManualEmployees` fails (network or 5xx), it returns `{ rows: [], ok: false }`. The roster then contains only sheet staff and `complete` is false. `acceptsRoster` accepts any non-empty roster, even a degraded one. The desktop does `setEmployees(payload.employees)` and writes it to `localStorage`. All manual employees vanish from the Personnel window and from the device cache until the next good sync (about 30 s cache). The "partial sync must not wipe the list" rule is applied only to the empty-roster case. The same failure makes `DELETE` return a misleading 404 "Сотрудник не найден".
**Fix:** When `manual.ok` is false, keep previously known manual entries. The simplest option is to have `acceptsRoster` reject a degraded roster that lacks entries currently shown, or have the client merge its existing `source === "manual"` entries back in when `payload.degraded` is true:
```ts
const keep = payload.degraded ? current.filter((e) => e.source === "manual" && !payload.employees.some((x) => x.id === e.id)) : [];
setEmployees([...payload.employees, ...keep]);
```

### WR-03: Manual-details save is non-atomic and misreports the cause of failure

**File:** `app/api/employees/route.ts:46-52`, `lib/portia-employees.ts:434-441`
**Issue:** (a) `saveEmployeeProfile` runs first, then `updateManualEmployee`. If the second call throws (any DB error other than 42501 or a missing table), the handler returns 500 "Не удалось сохранить профиль" although the profile was already stored. The client keeps the draft and the user retries, so this is harmless but confusing. (b) `updateManualEmployee` maps "zero rows updated" to `pending-database`, so a row deleted by another editor in the meantime shows "база данных ещё не обновлена", which is wrong. A manual row hidden behind a same-nickname sheet row has the same effect.
**Fix:** Return a distinct `not-found` status for zero rows when the table is known to exist (for example after a 42501/missing-table check), and map it to 404 or a different message. Wrap `updateManualEmployee` so a thrown error still returns the saved profile with `detailsPending: true`.

### WR-04: The employees tab becomes a dead end when the roster is empty, so nobody can be added

**File:** `components/portia-editor.tsx:1537-1538` (add button at ~1556)
**Issue:** `if (!selected || !draft) return <div className="editor-empty">...` returns before the "+ ВНЕ ТАБЛИЦЫ" button and the add form render. If the sheet is empty or down, or the last remaining person was just removed via `removeSelected` (`else setDraft(null)`), the editor shows only "В таблице пока нет сотрудников" and there is no way to add a manual employee. That is the very case the feature exists for (people outside the sheet).
**Fix:** Render the list aside, including the add button and form, even when there is no selection. Return the empty state only for the profile pane. Alternatively, render the add form inside the empty-state branch.

## Info

### IN-01: Stored nickname keeps the casing the editor typed, not Roblox's canonical name

**File:** `lib/portia-employees.ts:388-421`
**Issue:** `addManualEmployee` inserts and returns `input.nickname` as typed, for example `bOb`. `RobloxProfile` carries no canonical `name`, so the display and the stored row never match Roblox casing. Duplicate detection is case-insensitive, so this is cosmetic only.
**Fix:** Carry `user.name` into `RobloxProfile` and store `found.name`.

### IN-02: `sanitizeManualDetails` and `sanitizeManualEmployee` duplicate the text helper, and `{}` wipes the fields

**File:** `lib/portia-employees.ts:302-309,426-431`
**Issue:** The `text` closure is copy-pasted. Separately, `details: {}` or a missing field is sanitized to empty strings, so a PATCH containing `details: {}` clears title, rank and callsign. The current client always sends all three, so this is latent.
**Fix:** Hoist one `clip64` helper. In `sanitizeManualDetails`, return `null` unless all three keys are strings.

### IN-03: A malformed JSON body in POST and DELETE returns 500 instead of 400

**File:** `app/api/employees/route.ts:45,78`
**Issue:** `await request.json()` throws on bad JSON and falls into the catch, which returns 500 and logs an error. PATCH has the same behaviour, but the new handlers could easily be fixed.
**Fix:** `const body = await request.json().catch(() => null);` then validate with the existing 400 path.

### IN-04: The YouTube iframe has no `sandbox`, and the delete error path matches on a Russian substring

**File:** `components/portia-desktop.tsx:221`, `components/portia-editor.tsx:1596-1602`
**Issue:** (a) The embed iframe has no `sandbox` attribute. The id is validated, so this is hardening only: `sandbox="allow-scripts allow-same-origin allow-presentation allow-popups"` still works for nocookie embeds. (b) `removeSelected` tells a session-expired 403 apart from the "sheet employee" 403 with `payload.error?.includes("таблицы")`, which breaks silently if the server text is reworded.
**Fix:** Add the `sandbox` attribute, and return a machine-readable `code` (`"sheet"`) in the 403 body instead of matching on text.
