<objective>
Close the two owner-reported broadcast gaps (EDIT-02, «сохранение подтверждается» has to mean the save holds):
(1) a saved news post disappears: a late poll or a stale CDN copy reverts content, and a second editor's unsaved draft gets the
newest revision from its poll and overwrites the post without a 409; (2) adding a post duplicates text: broadcast handlers and the
format panel's stored commit address posts by render-time index while «+ НОВОЕ СООБЩЕНИЕ» inserts at the top.

"when I create a new post in the forum, it gets duplicated". Root causes, repros S1/S2/S3 and the live-DB evidence:
.planning/debug/forum-news-posts-vanish-duplicate.md. Both defects predate phase 3 (25bcbb2 / 5001944).
Fix the shared decisions, not the symptoms: a monotonic revision gate on GET, a base revision owned by the draft, and id-addressed
draft edits. The pure decisions live in lib/ with node tests. The existing 409 path and conflict text (D-07) stay as they are.
CDN/cache settings are out of scope (see Notes).
Output: lib/content-sync.ts and lib/editor-items.ts with tests; edited components/portia-desktop.tsx and components/portia-editor.tsx.
</objective>

## Notes

Operational warning for the owner (not changed by this plan):
- Local `next dev` (PC on localhost, phone over LAN) and the live site read and write the same production Supabase row
  (portia_content, id main). Every save from `next dev` is a production save.
- A save from `next dev` cannot purge the Netlify CDN: purgeCache has no NETLIFY_PURGE_API_TOKEN locally and purgeCacheTag swallows
  the error. /api/content is cached with s-maxage=300 and stale-while-revalidate=86400, so the live site can serve the pre-save copy
  for minutes. After this plan a tab that already knows a newer revision ignores that copy, but a fresh visitor still sees it, and an
  editor opened on it gets the conflict message when saving (no overwrite). CDN/cache settings are deliberately left as they are.
- For the owner, in Russian: «Правки из `next dev` сразу записываются в рабочую базу сайта, но кэш CDN они не сбрасывают: живой сайт
  может ещё несколько минут показывать старую копию. Проверяйте на тестовых сообщениях и удаляйте их после проверки.»

Assumptions and known limits:
- An answer with the same revision is accepted (only lower is dropped, as specified). Same revision means the same row, and the
  server-normalized copy still replaces the cached one.
- Revisions only grow through the PUT. If the row is deleted and re-created by hand, tabs whose cache holds a higher revision ignore the
  database until their site data is cleared.
- A poll sent while a save is in flight is accepted by the counter rule (only polls sent before the save are dropped, as specified). At
  worst it shows the other editor's newer save before ours returns; the next poll corrects the view, and the draft's base revision
  is not affected.
- The orphan formatting entries already in the live database (broadcast-mv1567ss, broadcast-mv2le2ht) stay. They are harmless because
  ids are unique, and this plan makes no database writes.
- Viruses, mutations (portiaTextKey.mutation is index-based) and recycle files are still index-addressed. They are outside these gaps.
- If another device deletes a post while this clean editor's panel targets it, and the owner then applies a style, one orphan
  formatting entry can be written. Rare; the post itself is not resurrected.
- The conflict path still asks the owner to copy edits and reload (existing UI, kept per the caller).
