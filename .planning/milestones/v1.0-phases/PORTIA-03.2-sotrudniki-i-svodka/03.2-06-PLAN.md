The block to approve (recorded by 03.2-01 in supabase/portia_setup.sql, after the nickname add-column line):

```sql
-- Editor ratings beyond knowledge (phase 03.2). Empty (null) means not rated yet; the site shows «—».
alter table public.portia_employee_profiles
  add column if not exists paws_rating integer check (paws_rating between 1 and 10),
  add column if not exists bio_rating integer check (bio_rating between 1 and 10),
  add column if not exists s_rating integer check (s_rating between 1 and 10),
  add column if not exists activity_rating integer check (activity_rating between 1 and 10),
  add column if not exists overall_rating integer check (overall_rating between 1 and 10);
-- PostgREST picks up the new columns without a restart.
notify pgrst, 'reload schema';
```

Impact: additive and nullable with no default. Existing rows get null (shown as «—»), nothing is rewritten, and the
lock is brief on a small table. Re-running is a no-op (if not exists). The existing table-level grants and RLS
policies (editors insert/update through portia_can_edit(), public select) cover the new columns; no grant or policy
changes. Rollback, only if reverting and only with the owner's go-ahead (it deletes any ratings entered since):
`alter table public.portia_employee_profiles drop column if exists paws_rating, drop column if exists bio_rating,
drop column if exists s_rating, drop column if exists activity_rating, drop column if exists overall_rating;`

Read-only column query for Task 2:

```sql
select column_name, data_type, is_nullable
from information_schema.columns
where table_schema = 'public' and table_name = 'portia_employee_profiles' and column_name like '%\_rating'
order by column_name;
```

Expected: six rows: activity_rating, bio_rating, knowledge_rating (is_nullable NO), overall_rating, paws_rating and
s_rating (the five new ones integer, is_nullable YES).
