## Warnings

### WR-01: Every 10 s poll replaces `content` with an identical copy, resetting the editor's history and re-running the toast effect

**File:** `components/portia-desktop.tsx:358-366` (with `components/portia-editor.tsx:584-594`, `lib/editor-history.ts:61-62`, `lib/content-sync.ts:3`)
**Issue:** `acceptFetchedContent` takes an equal revision (`revision >= knownRevision`), and `fetchContent` then always calls `setContent(fetched)` with a freshly built object. Before this plan the poll ran every 30 s, and plan 03.2-07 cut it to 10 s. The consequences of a new identity on each poll when nothing changed:
- The editor's sync effect (`[content, dirty, revision]`) dispatches `sync` whenever the draft is not dirty. The reducer compares `action.content === state.source` by identity, so it calls `initHistory`, which drops `past` and `future`. A user who edits, undoes everything (dirty is false again) and wants to redo loses the redo stack within 10 s. `repairSelections` and a re-clone of the whole draft also run each time.
- The toast effect (`[content.broadcasts, ...]`) re-runs and calls `setQuestToastItem(next)` with a new object, so the desktop re-renders every 10 s even with an unchanged toast.
- Every other `[content]` effect (for example the broadcast unread signature) re-runs.

**Fix:** Skip the apply when the answer is the revision already in hand and content is already shown. A ref is needed because `fetchContent` has no state dependencies:
```ts
const contentApplied = useRef(false); // set true where cached content or a fetch is applied
...
if (contentApplied.current && fetchedRevision === knownRevision.current) return;
```
Keep the equal-revision acceptance for the first apply and after the 409 reset (`knownRevision = -1`), where it matters.

### WR-02: A roster payload that lacks rating keys still turns into `null` ratings, and a save then clears the stored ratings

**File:** `lib/portia-employees.ts:45-55` (`profileOf`), `components/portia-editor.tsx:1380-1393`
**Issue:** This is the remaining part of the previous CR-01. The editor loads `/api/employees` through the CDN (`s-maxage` 600, `stale-while-revalidate` 86400). A copy generated before the rating columns shipped has no rating keys. `profileOf` maps them to explicit `null`, and the full draft is sent on save. `sanitizeEmployeeUpdate` reads `null` as "clear", so the six stored ratings are overwritten. The new guard also misses this payload: `payload.profilesRead === false` is false when the key is absent, so an old cached degraded copy passes too.
**Fix:** In the editor, reject a payload that does not have `profilesRead === true` (`if (payload.profilesRead !== true) throw ...`). This also covers the cached degraded copy. For the ratings, make `profileOf` keep `undefined` for a key the employee object lacks, and send only keys that differ from the loaded profile (see WR-04).

### WR-03: Edits typed while a save is in flight are discarded

**File:** `components/portia-editor.tsx:1417-1419`, inputs at `1483-1485`
**Issue:** Carried over from the previous review (WR-01) and not changed. The fields stay enabled during `state === "saving"`. When the PATCH answers, `setDraft(profileOf(payload.employee))` replaces the draft with the copy of what was sent. Anything typed meanwhile disappears and `dirty` goes false, so no guard fires.
**Fix:** Wrap the fields in `<fieldset disabled={state === "saving"}>`, or apply the server copy only when the current draft still equals the snapshot that was sent.

### WR-04: Every save writes all six ratings, so concurrent editors overwrite each other

**File:** `components/portia-editor.tsx:1405-1408` (`changes: draft`), `lib/portia-employees.ts:282`
**Issue:** Carried over (previous WR-05), unchanged. The roster is loaded once on mount; a stale editor or a second editor saves untouched ratings with stale values (last write wins). The server already treats absent keys as "unchanged".
**Fix:** Send only the keys where `draft[key] !== profileOf(selected)[key]`, plus `biography`/`photoUrl` when changed.

## Info

### IN-01: Escape handler on the toast works only when focus is already inside it

**File:** `components/portia-desktop.tsx:1717-1719`
**Issue:** `onKeyDown` is on the `<aside>`, but nothing moves focus there (the modal version used `showModal` and autofocus). For nearly every visitor Esc does nothing. Also `role="status"` is a live region and the toast contains buttons, which assistive tech does not expect there.
**Fix:** Either drop the handler or listen for Esc on `document` while the toast is shown. Use `role="region"` with an `aria-label` instead of `status`.

### IN-02: The 10 s poll is only as fresh as the CDN purge

**File:** `components/portia-desktop.tsx:39-40`, `app/api/content/route.ts:29`, `lib/portia-cdn.ts:10,20`
**Issue:** `/api/content` is served with `s-maxage=300, stale-while-revalidate=86400`, and the purge is deliberately non-fatal. If the purge fails, or in `next dev`/preview where it never runs, a visitor can see the previous content for minutes (or one extra poll behind through stale-while-revalidate). The `shortcut:` comment describes the CDN-cached poll but not this limit, so "a quest shows up within 10 s" is not guaranteed.
**Fix:** Add one line to the shortcut comment, or log purge failures so they are noticed.

### IN-03: Toast placement and scope

**File:** `app/portia.css:446-447`, `components/portia-desktop.tsx:520-522`
**Issue:**
- The CSS comment says the toast "never covers the system bar or window buttons". It is `position: fixed; top: 106px; z-index: 965` over windows that can be dragged anywhere, so it can cover a window's title controls.
- The `windows.editor.open` guard was removed, so an editor who saves a new active quest also gets the "НОВЫЙ КВЕСТ" toast over their own editor window.

**Fix:** Soften the comment. If the owner toast is unwanted, skip the toast while `windows.editor.open` (the toast effect already recomputes on later content changes).

### IN-04: Undo or redo of a type change leaves the Сводка editor on the wrong tab

**File:** `components/portia-editor.tsx:631-640` (`step`), `1062-1070`
**Issue:** Changing a card's type makes the view follow the card to its new category. Undo and redo are global and do not touch `broadcastEditorTab`, so undoing the type change sends the card back to the other category while the view stays, and the card disappears from the list with no hint.
**Fix:** In `step`, after computing the target, switch `broadcastEditorTab` to the category of the card that changed, or accept this (the tab counts already update).

### IN-05: `today` is `""` until the first clock tick

**File:** `components/portia-desktop.tsx:276`, `lib/broadcasts.ts:19-23`
**Issue:** Carried over (previous IN-04). With `today === ""`, `questState` marks every dated quest as upcoming for the first render, so badges and feed order are briefly wrong. The toast and the viewed-effect guard on `today`, but `broadcastFeed` and the badges do not.
**Fix:** Initialize `today` from `localDateKey(new Date())` in a lazy client-only state, or have `questState` return `"active"` for an empty `today`.
