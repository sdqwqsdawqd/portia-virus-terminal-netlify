## Что изменится на сайте

До применения (так сайт ведёт себя сейчас, когда функций доступа в базе нет):

- Гость видит закрытый экран «Заявка на доступ» с формой. Отправка показывает «Не удалось отправить заявку. Проверьте соединение и повторите.», потому что таблиц и функций заявок нет.
- В логе сервера один раз за запуск строка вида «… treating closure as ON (fail-closed) …».
- Редактор входит через «ВХОД ДЛЯ РЕДАКТОРА» и видит рабочий стол без карточки заявки.

После применения всех восьми файлов:

- Закрытие сайта включено по умолчанию (решение 3a, оно отменяет D-01). Менять флаг по-прежнему может только владелец.
- Гость видит форму заявки и статусы; одобренное устройство видит рабочий стол; редактор входит без заявки.

Отдельно: до Phase 25 закрытие скрывает только интерфейс рабочего стола. Маршруты `/api/content` и `/api/employees` по-прежнему отдают данные по прямому запросу (T-23-31). Закрытие API, CDN и чек-лист production — Phase 25, в эту инструкцию не входят.

- Правило: при первой ошибке остановитесь и пришлите текст ошибки, предварительно убрав из него секреты. Не повторяйте частично применённый файл вслепую.

## Проверка до применения

Только чтение.

- История миграций: `select version from supabase_migrations.schema_migrations order by version;`. Ожидаются три версии `20261101…` (Phase 16); версий из списка выше быть не должно.
- `supabase migration list` с удалённой целью (флаг цели смотрите в `--help`, см. следующий раздел).
- `supabase db push --dry-run` с удалённой целью: должны быть перечислены ровно ещё не применённые файлы списка выше.

Если истории нет, а файлы Phase 16 уже применены (см. `16-PRODUCTION-POSTFLIGHT.md`), сначала отметьте их по одной версии командой `supabase migration repair --status applied <версия>` с удалённой целью. Если dry-run показывает файлы `20261101…`, остановитесь: цель выбрана неверно или история потеряна.

## Как применить

Вариант A (рекомендуется): `supabase db push` с удалённой целью.

- В CLI v3 удалённая цель задаётся флагом `--remote`; без него целью будет локальная база. В более старых версиях используйте `--linked` или `--db-url "<строка подключения>"`. Флаги сверьте по `supabase db push --help`.
- Подтверждение не пропускайте и `--yes` не используйте.
- CLI применяет файлы по порядку и записывает версии в историю.

Вариант B: `psql "<строка подключения>" -v ON_ERROR_STOP=1 --single-transaction -f supabase/migrations/<файл>` по одному файлу в порядке списка. Затем для каждой применённой версии: `supabase migration repair --status applied <версия>`.

Дополнительно:

- SQL Editor в Dashboard годится только для проверок, не для применения.
- Файл 8 вручную повторно не запускайте (см. «Откат и выключение закрытия»).

## Секрет подписи заявок

Без секрета каждая заявка получает `unauthorized` (так задумано: fail closed). Шаг выполняется после файла 4.

1. Сгенерируйте случайное значение от 32 символов и проверьте длину до вставки: слишком короткое значение вызвало бы ошибку ограничения, а Postgres печатает строку с секретом в тексте ошибки и в логах.
2. Выполните вставку от имени владельца базы через `psql`, а не сохранённым запросом в SQL Editor (чтобы значение не осталось в истории Dashboard). Вставка со страховкой длины, точный текст из шапки фундамента:
   `insert into public.portia_access_secrets (name, secret) select 'submit', v from (select '<значение>'::text as v) t where length(v) >= 32 on conflict (name) do update set secret = excluded.secret, updated_at = now();`
3. Ожидается `INSERT 0 1`. Ответ `INSERT 0 0` значит, что значение короче 32 символов и ничего не сохранено.
4. Положите то же значение в `PORTIA_ACCESS_SUBMIT_SECRET` (`.env.local` и Netlify).

## Проверки после применения

Владелец выполняет сам; всё только чтение. Результаты не записываются в GSD как пройденные, пока их не принесёт владелец.

1. Версии: `select version from supabase_migrations.schema_migrations where version >= '20261104000000' order by version;` — 8 строк.
2. Таблицы: `select table_name from information_schema.tables where table_schema = 'public' and table_name like 'portia\_access\_%' order by table_name;` — пять имён: `portia_access_journal`, `portia_access_people`, `portia_access_requests`, `portia_access_secrets`, `portia_access_settings`.
3. Функции доступа: `select count(*) from pg_proc p join pg_namespace n on n.oid = p.pronamespace where n.nspname = 'public' and p.proname like 'portia\_access\_%';` — ожидается 18.
4. Защищённые функции «Повышения»: `select count(*) from pg_proc p join pg_namespace n on n.oid = p.pronamespace where n.nspname = 'public' and (p.proname like 'portia\_promo\_secure\_%' or p.proname in ('portia_promo_participant_key', 'portia_promo_test_proof_valid'));` — ожидается 10. Числа 18 и 10 взяты из эталонного отпечатка `supabase/fingerprint/expected/portia.fingerprint.json`, как в тесте.
5. Закрытие включено:
   - `select public.portia_access_closure_enabled();` — true;
   - `select closure_enabled, updated_by is null as never_toggled from public.portia_access_settings where id = 'main';` — true | true;
   - `select column_default from information_schema.columns where table_schema = 'public' and table_name = 'portia_access_settings' and column_name = 'closure_enabled';` — true.
6. Права:
   - `select has_function_privilege('anon', 'public.portia_access_closure_enabled()', 'execute');` — true;
   - `select has_function_privilege('anon', 'public.portia_access_set_closure(boolean)', 'execute');` — false;
   - `select has_function_privilege('anon', 'public.portia_access_submit_request(text, text, text, text, bigint, text)', 'execute');` — true.
7. Секрет без вывода значения: `select count(*) as submit_secret_ok from public.portia_access_secrets where name = 'submit' and length(secret) >= 32;` — 1.
8. Кэш PostgREST: POST на `<NEXT_PUBLIC_SUPABASE_URL>/rest/v1/rpc/portia_access_closure_enabled` с заголовками `apikey` (публикуемый ключ проекта) и `Content-Type: application/json` и телом `{}`, например через curl. Ответ `true`. Ответ с кодом PGRST202 значит, что кэш не перезагружен: повторите `notify pgrst, 'reload schema';` и подождите.
9. Необязательно, отпечаток схемы: выполните `supabase/fingerprint/portia_schema_fingerprint.sql` в `begin read only; … rollback;`, сохраните результат в JSON и сравните: `node scripts/phase16-fingerprint-compare.mjs <снятый.json> supabase/fingerprint/expected/portia.fingerprint.json`. Любое расхождение классифицирует человек.

## Откат и выключение закрытия

Откат только вперёд, откатывающей миграции нет.

- Экстренно выключить закрытие (изменение данных, делает владелец): `update public.portia_access_settings set closure_enabled = false, updated_at = now(), updated_by = coalesce(updated_by, gen_random_uuid()) where id = 'main';`. Поле `updated_by` ставится намеренно: пока оно пустое, повторный ручной запуск файла 8 снова включил бы закрытие (находка RLS23-05, принята).
- Включить обратно: тот же оператор с `true` вместо `false`.
- Выбор владельца сохраняет только `portia_access_set_closure` (Phase 25, переключатель на сайте, только владелец). Файл 8 вручную повторно не запускайте: при ручном выключении через Studio или SQL Editor без `updated_by` он переключит закрытие обратно.
- Шаг 3 «ожидается false» из 21-MIGRATION-APPLY.md заменён проверкой 5 выше: после файла 8 значение true.
