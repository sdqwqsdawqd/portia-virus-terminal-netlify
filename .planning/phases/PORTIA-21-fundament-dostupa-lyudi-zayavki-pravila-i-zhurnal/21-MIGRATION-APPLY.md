## Секрет подписи заявок (шаг владельца при применении)

Решение владельца 2026-11-09 (RLS21-01, вариант 1а): заявки подписывает сервер сайта, база проверяет подпись.

1. Сгенерировать случайное значение, 32 символа и больше.
2. Выполнить вставку в базе от имени владельца базы, предпочтительно через `psql`, а не сохранённым запросом в SQL Editor Supabase (чтобы текст со значением не остался в истории Dashboard). Вставка со страховкой длины, точный текст в шапке миграции (блок OWNER STEP):
   `insert into public.portia_access_secrets (name, secret) select 'submit', v from (select '<значение>'::text as v) t where length(v) >= 32 on conflict (name) do update set secret = excluded.secret, updated_at = now();`
3. Ожидаемый ответ `INSERT 0 1`. Ответ `INSERT 0 0` значит, что значение короче 32 символов и ничего не сохранено.
4. Положить то же значение в серверную переменную Netlify `PORTIA_ACCESS_SUBMIT_SECRET`.
5. Пока секрета нет, каждая заявка получает `unauthorized`. Фаза 21 не добавляет маршрута, который подаёт заявки (он появится в Phase 23), так что на поведение сайта это сейчас не влияет.

## Откат

Только вперёд. Откатывающей миграции нет и применять её автоматически нельзя.

- Если когда-либо появится вызывающий `portia_promo_register_attempt` или `portia_promo_bind_device`, права возвращает новая forward-only миграция (grant), а не правка замороженного файла.
- Удаление объектов доступа (таблицы `portia_access_*`, функции, триггеры) только по отдельному решению владельца; журнал решений по замыслу (D-07) хранится навсегда и защищён от update, delete и truncate.
- Выключить закрытие сайта можно в любой момент владельцем через `portia_access_set_closure(false)` (в фазе 21 оно и так выключено).
- Секрет подписи заменяется тем же оператором с новым значением и новой серверной переменной; запросы со старой подписью отклоняются.

## Принятые риски

Владелец подтверждает или отклоняет каждый пункт по номеру на чекпоинте.

1. **Самоодобрение из браузера без входа (21-03).** Самоодобрение определяется по связи с аккаунтом. Ник, поданный из браузера без входа, связи не несёт, поэтому редактор, одобряющий собственную заявку, поданную без входа, не распознаётся как «сам». Смягчение: журнал решений и отзыв.
2. **Ограниченный редактор может выдавать уровень до 5 до Phase 22 (RLS21-05).** Вкладки `users` ещё нет в `lib/editor-tabs.ts`, проверка равна `portia_can_edit()`; решать может любой редактор (D-02), «выше своего уровня» фактически пусто, потому что все решающие имеют 5. Смягчение: журнал, отзыв, вкладка в Phase 22.
3. **Нейтральный `unavailable` раскрывает, что ник сейчас заблокирован (RLS21-06).** Раскрывается наличие заявки или отказа менее часа назад и превышение 3 заявок в сутки; одобренные люди не раскрываются. Смягчение: зондирование шумное (создаёт заявки), доступ только через маршрут Phase 23 с лимитами.
4. **Флаг закрытия читается кем угодно (T-21-20), кто его переключил, не журналируется (T-21-21, D-07).** Отдаётся одна булева без метаданных; последнее изменение хранится в строке (D-08). Вопрос журнала переключений вернётся в Phase 25 по желанию владельца.
5. **Строки журнала нельзя удалять, в том числе на staging.** Это следствие D-07 и триггеров: очистка тестового стенда между прогонами не может удалять журнал, стенд надо пересоздавать. Владелец таблицы и суперпользователь могут отключить триггер (вне модели API-ролей, принято, RLS21-03).
6. **Повтор подписи в течение 300 секунд (RLS21-12).** Привязан к token_hash, новую строку не создаёт, кроме случая после `clear_cooldown` для того же устройства.
7. **Секрет подписи хранится открытым текстом в закрытой таблице (RLS21-13).** Виден роли postgres, Dashboard и резервным копиям; текст вставки может попасть в лог при `log_statement = all` (BLOCKED, проверка настроек логов). Смягчение: вставка через `psql` со страховкой длины.
8. **Устаревшие скрипты установки (RLS21-14).** `supabase/portia_setup.sql` и `supabase/phase14_apply.sql` по-прежнему выдают `portia_promo_bind_device` роли anon. Не разворачивать их вместо миграций.
9. **Группировка по /48 (IPv6) и /24 (IPv4) (RLS21-08, RLS21-16).** Один злоумышленник в общем пуле оператора может заблокировать соседей на сутки десятью запросами. Снимается проверкой человека в Phase 23.
10. **Адаптер Netlify (SEC-08).** `next` и `eslint-config-next` подняты до 16.4.5 (`255ec54`); версию `@netlify/plugin-nextjs` не ниже 5.16.6 можно подтвердить только в логе деплоя владельца: BLOCKED (OWNER).

Переносится в Phase 23 как требования, в фазе 21 не выполнено:

- Перед вызовом `portia_access_submit_request` маршрут применяет проверку человека (например Turnstile) или второй грубый лимит (/16 для IPv4, /32 для IPv6).
- Каждый ответ `unauthorized` пишется в журнал тревог.
- Адрес берётся только из `x-nf-client-connection-ip`; при отсутствии заголовка или группе `unknown` маршрут отвечает нейтральной ошибкой и пишет тревогу.
- Реальный формат и неподменяемость `x-nf-client-connection-ip` на Netlify проверяются на стенде.
