# Phase 03.3: Сотрудники вне таблицы и гайды в Информации - Context

**Gathered:** 2026-10-18
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase delivers two things.

1. **Employees outside the sheet.** In «Сотрудники», an editor can add a person who is not in the Google Sheet. The person is added by Roblox nickname. The editor fills in title, rank and callsign by hand and can set a custom photo. Ratings and biography work as they do for everyone else. A manually added person can be removed. A person from the sheet cannot be removed.

2. **Guides in «Информация».** A category gets one level of subcategories. For example, «Что такое вирус» has «Сам вирус» and «Способы распространения» under it. A subcategory is built from blocks: text, photo, YouTube video and a classification table. The goal is detailed guides for newcomers.

This phase does not include text formatting. That is phase 5 and stays out of scope.

</domain>

<decisions>
## Implementation Decisions

### Employees outside the sheet
- **D-01: Fields for a manual employee.**
  - The editor enters a Roblox nickname. The Roblox user is looked up and the avatar comes from Roblox, as for sheet employees.
  - Title (звание), rank (ранг) and callsign (позывной) are typed in by the editor.
  - Photo, ratings and biography are the same profile as for everyone else.
- **D-02: Placement in the list.**
  - Manual employees go in the same «Сотрудники» list, after the sheet employees.
  - Their card has a small «ВНЕ ТАБЛИЦЫ» mark.
  - Only they have a delete action. Sheet employees never show one, and the server refuses to delete them.
- **D-03: Validation when adding.**
  - If Roblox does not find the nickname, the add is refused with «Ник не найден».
  - If the person is already in the sheet or already added, the add is refused with «Уже есть в списке».
  - If a manual person is later added to the sheet, they count as a sheet employee and keep their photo, ratings and biography. Their stable id is `roblox-<userId>`.
  - **Reversibility:** costly. Profiles are keyed by `employeeId`, and changing the matching later means migrating stored rows.
- **D-04: Photo priority.**
  - A custom photo replaces the Roblox avatar.
  - Removing the custom photo shows the Roblox avatar again.
  - This is the same rule as for sheet employees today.
- **D-05: Who can add and remove.** Anyone with editor access (`getEditorAccess().canEdit`), the same gate as profile saves.

### Guides in «Информация»
- **D-06: Structure.**
  - One level only: category → subcategories.
  - A category keeps its own title and text.
  - Subcategories are ordered and can be reordered the way sections are today, with the drag handle.
- **D-07: Subcategory content is a list of blocks in any order.**
  - Block types: text, photo, YouTube video, classification table.
  - The editor adds, removes and reorders blocks.
- **D-08: The classification block.**
  - It is a «признак — значение» table, for example «Путь передачи — воздушный».
  - The editor adds and removes rows.
- **D-09: YouTube.**
  - The video plays in an embedded player inside the window.
  - A click or link opens the same video on youtube.com in a new tab.
  - Only YouTube URLs are accepted.
- **D-10: Photos in guides.** They are uploaded the same way as existing site images.
- **D-11: Navigation.**
  - A tree in the left column of «Информация»: a category expands to show its subcategories.
  - Selecting a subcategory shows its blocks on the right.
- **D-12: Old content.** Existing flat `infoSections` keep working as categories with no subcategories. Nothing already published is lost.

### Claude's Discretion
- Where manual employees are stored: a new Supabase table, or a flag on `portia_employee_profiles`. Any production SQL needs the owner's approval first, as in 03.2-06.
- The data shape of subcategories and blocks inside the content payload. It must be normalized for untrusted input, as `normalizeBroadcasts` does.
- Embed details: use `youtube-nocookie.com` and lazy load, parse video ids from both `youtube.com/watch?v=` and `youtu.be/`, and update any CSP or `frame-src`.
- How search treats subcategories, as long as existing «Информация» search hits still work.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `resolveRobloxProfiles(usernames)`: Roblox nickname → user id and avatar. Reuse it to validate a manual add.
- `/api/uploads`, plus the editor's upload helper around line 741: photo upload for custom employee photos and guide photos.
- `OrderDragHandle` and `moveArrayItem`: reorder subcategories and blocks.
- `updateById` and `makeId`: id-based draft edits.
- `ConfirmDialog`: confirm before deleting a manual employee or a block.
- The `normalizeBroadcasts` pattern: strict normalization of new nested content.

### Established Patterns
- Content is one JSON payload in `portia_content` (id `main`) and is saved through `/api/content` with a revision gate. Guides live there.
- Employees come from a live merge of the sheet and Roblox, with profiles stored in Supabase. Manual employees must merge into the same roster and cache (`employeesCacheTag` purge).
- Production DDL is gated by the owner and must be idempotent (`if not exists`).
- Visible text is in Russian. The team is an отдел, never an отряд.

### Integration Points
- The `/api/employees` roster merge: add manual employees and mark their source.
- The editor's «Сотрудники» tab: an add form and a delete action.
- The info window and the editor's «Информация» tab: tree navigation and the block editor.
- Global search over info content.

</code_context>

## Specific Ideas

- Example category: «Что такое вирус» → «Сам вирус», «Способы распространения», with classification rows inside.
- The guides are for people who don't know the system yet, so step-by-step text with screenshots and videos in between matters. This is why blocks can go in any order.
