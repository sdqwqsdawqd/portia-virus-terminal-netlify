# Phase PORTIA-03.2: Code Review Report

**Reviewed:** 2026-10-18
**Depth:** standard (diff `ea1c583..HEAD`, `.planning` excluded; no CLAUDE.md in the project)
**Files Reviewed:** 13
**Status:** issues_found

## Summary

The new rating columns, the missing-column retry and the quest/date helpers are mostly sound. In particular:

- Rendered conditions are plain React text children, so there is no XSS.
- Seen-quest ids from localStorage are type-filtered.
- The retry only fires for PGRST204 and 42703 and rethrows everything else.

The main concern is data loss on employee save. `knowledge_rating` is now hidden from editors, so a reset to 1 can no longer be noticed. The save path has two ways to overwrite stored values: a degraded roster used as the baseline, and a stale closure after the unsaved-edit dialog.

## Critical Issues

### CR-01: Employee save can silently reset knowledge_rating (and wipe all ratings and biography) from a degraded roster or an omitted field

**File:** `lib/portia-employees.ts:254-258,296-308` and `components/portia-editor.tsx:1335-1347`, `app/api/employees/route.ts:41`
**Issue:** `knowledge_rating` is no longer shown, but it is still written on every save.

1. `sanitizeEmployeeUpdate` turns a missing, null or non-numeric `knowledgeRating` into `1`. `Number(undefined)` is NaN, which becomes 1, and `Number(null)` is 0, which clamps to 1. `saveEmployeeProfile` then always puts `knowledge_rating` into `base`. Any PATCH that omits the field, such as an older cached editor bundle, resets the stored value to 1. The test `sanitizeEmployeeUpdate({})?.knowledgeRating === 1` (portia-employees.test.ts:152) locks this in.
2. `loadEmployees` returns a degraded-but-HTTP-200 roster when the profile read fails (`profiles === null`). Every employee then gets `emptyProfile`: knowledge 1, all six ratings null, empty biography. `GET /api/employees` reports `degraded: true`, but the editor fetch (portia-editor.tsx:1337-1346) ignores it. It seeds `draft = profileOf(first)` from that blank profile. The editor sees no difference, because the knowledge field is hidden, and a plain save upserts knowledge=1, six nulls and an empty biography over the real row. The PATCH route does not check `complete` either.
3. `profileOf` maps a missing rating (`?? null`) to an explicit `null`. The server reads that null as "clear the rating". A roster served from the CDN or localStorage cache before the columns existed therefore clears stored ratings on save. This contradicts the `EmployeeUpdate` doc comment, "ratings missing here are not changed".

**Fix:**
```ts
// EmployeeUpdate: knowledgeRating becomes optional like the other ratings
const knowledgeRating = Number(candidate.knowledgeRating);
if (candidate.knowledgeRating != null && Number.isFinite(knowledgeRating)) update.knowledgeRating = clamp(knowledgeRating);
// saveEmployeeProfile: add knowledge_rating to the row only when update.knowledgeRating !== undefined
```

- In the editor, refuse to build a draft when `payload.degraded` is true (show "Данные не синхронизированы, обновите позже") and disable the save button.
- In the PATCH route, return 503 when `complete` is false.
- In `profileOf`, keep `undefined` for ratings the employee object lacks instead of coercing to null, and send only the changed fields.

### CR-02: After "СОХРАНИТЬ" in the unsaved-edit dialog, a stale `selected` is written back into the draft and re-marks the profile dirty

**File:** `components/portia-editor.tsx:1397-1405` (`continueLeave`) and `1432-1440` (save then continueLeave)
**Issue:** `save()` ends with `setDraft(profileOf(payload.employee))` and updates `employees`. The `.then` callback then calls `continueLeave`, which is the closure from the render in which the button was clicked. In that closure `selected` is the pre-save employee. The `else` branch runs `setDraft(profileOf(selected))`, so the draft is reset to the OLD stored values while `employees` holds the NEW ones. `dirty` becomes true again, and the effect at line 1346 re-sets the parent's `employeeDirty` to true right after `onLeave(true)` cleared it.

- For a tab switch this is harmless, because the tab unmounts.
- For the window-close path with dirty content, `closeAsked` is still true. `employeeDirty` is true again, so the employee dialog reappears for data that was just saved. Pressing СОХРАНИТЬ there writes the old values over the new ones: data loss.
- For a close with clean content, `onCloseApproved` fires. If the editor stays mounted (minimize or close animation), the draft is left stale.

**Fix:** After a successful save, do not reset the draft at all:
```ts
const continueLeave = (saved = false) => {
  ...
  else { if (!saved) setDraft(profileOf(selected)); onLeave(true); }
};
// caller: if (saved) continueLeave(true); else cancelLeave();
```
Alternatively, have `save()` return the saved employee and use it.

## Warnings

### WR-01: Edits typed while a save is in flight are silently discarded

**File:** `components/portia-editor.tsx:1356-1385`, inputs at 1451-1453
**Issue:** The inputs stay enabled while `state === "saving"`. When the PATCH answers, `setDraft(profileOf(payload.employee))` replaces the draft with the server copy of what was sent. Anything typed or selected in between disappears, and `dirty` becomes false, so no guard fires.
**Fix:** Disable the fields (a `<fieldset disabled={state === "saving"}>`), or only replace the draft when it still equals the snapshot that was sent.

### WR-02: `normalizeBroadcasts` does not normalize the fields that matter for rendering and visibility

**File:** `lib/portia-content-normalize.ts:83-94`
**Issue:** The filter type guard only checks "non-null object", so arrays pass too. The `...item` spread keeps `id`, `type`, `title`, `body` and `published` as-is, together with any unknown keys.

- `published: "false"` or `1` is truthy, so the item is shown to visitors.
- A non-string `title` or `body` can crash the React render. An object child throws "Objects are not valid as a React child".
- A missing `id` gives an undefined key and an id that collides with the seen-quest bookkeeping.
- An unknown `type` falls into the quests tab via `broadcastTabOf`.

This is the client-side defence for cache and API data, which the phase set out to harden.
**Fix:** Build the object explicitly:
```ts
.filter((i) => i && typeof i === "object" && !Array.isArray(i) && typeof i.id === "string" && i.id)
.map((i) => ({
  id: i.id,
  type: i.type === "quest" || i.type === "task" ? i.type : "news",
  title: typeof i.title === "string" ? i.title : "",
  body: typeof i.body === "string" ? i.body : "",
  published: i.published === true,
  important: i.important === true,
  startsAt: normalizeDay(i.startsAt),
  endsAt: normalizeDay(i.endsAt),
  conditions: typeof i.conditions === "string" ? i.conditions.slice(0, 4000) : "",
}))
```

### WR-03: `markQuestsSeen` prunes seen ids against whatever content the current tab has, so a stale tab can resurrect the popup

**File:** `lib/broadcasts.ts:57-60` and `components/portia-desktop.tsx:489-494`
**Issue:** `rememberActiveQuests` rewrites localStorage keeping only ids present in this tab's `content.broadcasts`. A tab running stale cached content that lacks a newly published quest Q, or a transient content window, drops Q's id from storage. This happens when it merges storage with its own ref and prunes. Reloading another tab then pops Q up again, which breaks the "once per id" rule. The same happens if a quest is deleted and later restored.
**Fix:** Prune only when the content is known to be fresh (`revision >= knownRevision`, a live fetch). Or cap the list (for example the last 200 ids) instead of pruning by existence.

### WR-04: The "saved without the new ratings" notice omits a rating that was also not saved

**File:** `components/portia-editor.tsx:1458`
**Issue:** `employeeRatings.slice(1)` assumes the first rating (`paws_rating`) already existed in the database. This phase's SQL adds `paws_rating` too (`supabase/portia_setup.sql:32-38`), so when the migration is absent all six are dropped, but the message lists only five. The production columns are reported as applied, so this path is rarely hit, but the retry code and message are still shipped.
**Fix:** Use `employeeRatings.map(...)`. Or delete the retry and `ratingsPending` path once the migration is confirmed in production.

### WR-05: Every save sends and writes all six ratings, so concurrent editors overwrite each other (last write wins)

**File:** `components/portia-editor.tsx:1356-1367` (body is `changes: draft`), `lib/portia-employees.ts:296-308`
**Issue:** The roster is loaded once on mount and held in component state. Two editors, or one editor with a stale roster, each save the full profile. A rating that editor B never touched is overwritten with its stale value, now across six numeric fields that are no longer visible together with the hidden knowledge value.
**Fix:** Send only the keys whose draft value differs from `profileOf(selected)`. The server already treats absent keys as "unchanged".

## Info

### IN-01: Conditions text loses line breaks in the Сводка card but not in the popup

**File:** `app/portia.css:412` against `448`
**Issue:** `white-space: pre-line` is set only for `.quest-popup .broadcast-conditions p`. The card in the Сводка list collapses newlines in the same plain-text field.
**Fix:** Move `white-space: pre-line` to `.broadcast-conditions p`.

### IN-02: Date validation accepts impossible dates, and nothing keeps start before end

**File:** `lib/portia-content-normalize.ts:79-80`, `components/portia-editor.tsx:1029`
**Issue:** `dayPattern` accepts `9999-99-99` and `2026-02-31`. The editor only sets the `min` attribute on the end date, so `startsAt > endsAt` is storable. Such a quest is "upcoming" until its start and "finished" afterwards, and it is never active. A start of `9999-99-99` hides a quest forever.
**Fix:** Validate with `new Date(\`${v}T00:00:00Z\`).toISOString().startsWith(v)`, and drop or swap an inverted pair.

### IN-03: Popup details

**File:** `components/portia-desktop.tsx:489-494,231-238,328-340`
**Issue:**
- `dismissQuestPopup` marks every active quest in the current `content` as seen, including quests that arrived through the 30-second sync after the popup opened and were never shown.
- The popup keeps its own quest snapshot even if that quest becomes unpublished or finished while the popup is open.
- A click on the dialog's own padding counts as a backdrop click (`target === currentTarget`) if the dialog has padding.
**Fix:** Mark only the shown quest plus the ids counted in `more`, which means storing the shown ids with the popup state.

### IN-04: `today` is `""` until the first client tick

**File:** `components/portia-desktop.tsx:303-305,453-460`, `lib/broadcasts.ts:19-23`
**Issue:** With `today === ""`, `questState` treats every quest that has a start date as "upcoming" (`"" < startsAt`). Anything rendered before the first effect would show the wrong badge and feed order for a moment. The popup and the viewed-effect guard on `today`, but `broadcastFeed` and the badges do not.
**Fix:** Initialize `today` lazily with `localDateKey(new Date())` on the client, or have `questState` return "active" for an empty `today`.
