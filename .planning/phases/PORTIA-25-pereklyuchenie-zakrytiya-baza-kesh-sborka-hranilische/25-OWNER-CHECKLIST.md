# Phase 25: чек-лист владельца — включение закрытия, откат

Дата записи: 2026-11-16. Документ для владельца: что применять, в каком порядке, как проверить и как откатиться, когда закрытие содержимого включается на вашей базе и на сайте.

**Агент не применил ничего и нигде**: ни SQL, ни CLI, ни подключения к какой-либо базе, ни деплоя, ни сброса CDN. Всё ниже — текст. Решения о применении и включении принимает владелец (D-03, D-07). Рекомендация: сначала изолированный тестовый проект и deploy preview, потом production; решение за владельцем.

Правило: при первой ошибке остановитесь и пришлите текст ошибки, предварительно убрав из него секреты. Не повторяйте частично применённый файл вслепую.

Все проверки в этом документе — только чтение. Ни одна из них не выполнена: пока их не принесёт владелец, они остаются BLOCKED (staging) / ОЖИДАЕТ ВЛАДЕЛЬЦА и не записываются в GSD как пройденные.

## Что изменится на сайте

До включения (так сайт ведёт себя сейчас): рабочий стол закрывается только интерфейсом; `/api/content` отдаёт содержимое по уровню посетителя, но аноним по публичному ключу Supabase читает таблицы `portia_content`, `portia_employee_profiles` и `portia_manual_employees` напрямую, а в бакете `portia-media` может получить список файлов.

После всех шагов:

- Аноним с публичным ключом не читает три таблицы и не получает список файлов `portia-media`; содержимое отдаёт только сервер сайта через подписанные функции `portia_content_read` и `portia_employees_read`.
- Закрытые ответы сайта `no-store` и без тегов кэша; старые копии CDN сброшены владельцем по тегам `portia-content` и `portia-employees`.
- Страница и сборка не содержат содержимого; без базы одобренный посетитель видит пустой рабочий стол со строкой «Данные временно недоступны».
- Закрытие включено; сайт не закрывается для своих ни на минуту (D-05): одобренные устройства и редакторы работают на каждом шаге.
- Картинка открывается по точной ссылке; редактор может «сменить адрес картинки» (D-13).

Часть этих пунктов (кэш устройства по человеку и уровню, скан сборки на маркеры содержимого) доставляют планы 25-08 и 25-09: применяйте чек-лист к коду, в котором они выполнены.

Что не меняется и что остаётся ограничением — в разделе «Известные ограничения» и в `25-RELEASE-NOTES.md`.

- `/api/content` у одобренного отвечает ошибкой дольше 5 минут.

Любой из трёх признаков — раздел «Откат», быстрый уровень, затем при необходимости аварийный.

### Шаг 14. Сбросить CDN по двум тегам

Старые ответы прежнего кода могли остаться в CDN (до `s-maxage` плюс `stale-while-revalidate`); сбросить их может только владелец. Выполнять только после шага 13:

`curl -sS -X POST "https://api.netlify.com/api/v1/purge" -H "Authorization: Bearer $NETLIFY_AUTH_TOKEN" -H "Content-Type: application/json" -d "{\"site_id\":\"$NETLIFY_SITE_ID\",\"cache_tags\":[\"portia-content\",\"portia-employees\"]}"`

Значения переменных `NETLIFY_AUTH_TOKEN` и `NETLIFY_SITE_ID` берите из своего хранилища секретов, в чат и в документы их не копируйте. Лимит Netlify: каждый тег можно сбросить два раза за 5 секунд (ответ 429 — подождите и повторите). Запасной путь, если API недоступен: в панели Netlify «Clear cache and deploy site». Сбрасывать нужно всегда: документация Netlify не говорит, сбрасывает ли деплой `durable`-записи. Проверка: `С5` (`Cache-Status` не показывает попадания старой копии на `/api/employees` и `/api/content`).

### Шаг 15. Сменить адрес картинки (проверка хранилища)

В редакторе на одной тестовой записи с картинкой нажмите «Сменить адрес картинки» и сохраните запись. Проверки: `С6` (новая ссылка отдаёт `Cache-Control` со сроком около года, старая после сохранения отвечает 404).

## Секрет подписи заявок и чтения

Без секрета подписанные функции и заявки отвечают `unauthorized` (fail closed). Шаг выполняется после файла 4 (шаг 5 выше).

1. Сгенерируйте случайное значение от 32 символов и проверьте длину до вставки: слишком короткое значение вызвало бы ошибку ограничения, а Postgres печатает строку с секретом в тексте ошибки и в логах.
2. Выполните вставку от имени владельца базы через `psql`, а не сохранённым запросом в SQL Editor (чтобы значение не осталось в истории Dashboard). Вставка со страховкой длины:
   `insert into public.portia_access_secrets (name, secret) select 'submit', v from (select '<значение>'::text as v) t where length(v) >= 32 on conflict (name) do update set secret = excluded.secret, updated_at = now();`
3. Ожидается `INSERT 0 1`. Ответ `INSERT 0 0` значит, что значение короче 32 символов и ничего не сохранено.
4. Положите то же значение в `PORTIA_ACCESS_SUBMIT_SECRET` (`.env.local` и переменные Netlify). Значения секретов никуда не записывайте и не присылайте.

## Откат

Откат только вперёд: откатывающей миграции нет, есть быстрый выключатель и аварийный файл. Оператор выключения закрытия — SQL владельца, изменение данных.

### Быстрый откат

Выключить закрытие (D-08):

`update public.portia_access_settings set closure_enabled = false, updated_at = now(), updated_by = coalesce(updated_by, gen_random_uuid()) where id = 'main';`

Что он лечит: редактор не может войти, одобренный видит экран заявки, закрытие мешает своим. Анонимное прямое чтение таблиц при этом остаётся закрытым, сайт читает через сервер. Что он не лечит: если сломано само чтение через сервер, ломаются и открытый, и закрытый режимы — тогда нужен аварийный откат. Включить обратно: тот же оператор с `true` вместо `false` (шаг 13). Выбор владельца файл 8 уважает: его повторный запуск закрытие не включит.

Признаки, что пора откатываться (D-10): редактор не может войти; одобренный сотрудник видит экран заявки; `/api/content` у одобренного отвечает ошибкой дольше 5 минут.

### Диагностика перед аварийным откатом

Только чтение: совпадают ли значения `PORTIA_ACCESS_SUBMIT_SECRET` в Netlify и строка `'submit'` в базе (длина не меньше 32; `П4`); применён ли файл 9 (`П3`); как отвечает функция на тестовый вызов (`П7`); не рассинхронизированы ли часы (подпись действует 300 секунд назад и 60 вперёд).

### Аварийный откат

Только если сломано чтение через сервер и быстрый откат не помог. Порядок строго такой:

1. В Netlify: «Publish deploy» для предыдущего деплоя (старый код читает таблицы напрямую и не знает функций чтения). Новый код с аварийным файлом анонимные права не использует.
2. Затем применить аварийный файл одной транзакцией:
   `psql "<строка подключения>" -v ON_ERROR_STOP=1 --single-transaction -f supabase/emergency/20261115000200_portia_emergency_restore_anon_read.sql`
   Файл в `supabase/emergency/`, а не в `supabase/migrations/`: он не миграция, и пакетное применение миграций его не затрагивает. Он возвращает анониму чтение трёх таблиц (текст политик — как в базовой миграции); листинг `portia-media` он не возвращает, сайту он не нужен.
3. Цена аварии: анонимное прямое чтение таблиц снова открыто, содержимое доступно по публичному ключу в обход уровней. После аварии вернуться к контракту можно только новым раскатом: чек-лист заново с шага 8, не повторным запуском файла 10.
4. Не удаляйте аварийный файл после использования и не правьте его: любое изменение SQL требует обновить закреплённый sha256 ниже (тест это проверяет).

## Известные ограничения

Полный текст — в `25-RELEASE-NOTES.md`. Главное для владельца:

- сохранённая ссылка на картинку продолжает открываться у человека, потерявшего доступ, пока редактор не сменит адрес (D-11, по образцу SEC-07);

- срок жизни серверного снимка сотрудников (5 минут, 30 секунд для неполного) — допущение `[ASSUMED]`, не измерено на стенде.
