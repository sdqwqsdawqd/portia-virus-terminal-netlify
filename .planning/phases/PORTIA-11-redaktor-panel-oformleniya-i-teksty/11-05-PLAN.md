<objective>
Let the owner reorder table rows and swap the two table columns in the editor, with the order kept on the site (EDIT-07; owner decisions D-18, D-19).

Purpose: a table built in the wrong order now has to be retyped. The owner wants the familiar ≡ on rows and on the two column headers.

Output: row ids in the content layer, a row ≡, a column swap handle, an empty-table state, harness check `table`, and a UI-SPEC amendment.

Planner decisions (Claude's discretion «способ хранения перестановки столбцов»):
1. A column swap swaps `key` and `value` in every row. There is no schema flag and no change to the public render: the site already shows `dt` = key (the first column) and `dd` = value. «Признак» and «Значение» are the names of the two positions, so after a swap the left column is still called «Признак» and holds the former values. Undo is a second swap, so the decision is `reversible`.
2. Rows get a stable `id`. Rows are keyed by index today. `OrderDragHandle` resyncs its index from props after every render, so with index keys a dragged row's handle stays in its old DOM slot: the next pointer move swaps the row back, and keyboard focus stays on the old slot. A normalizer-backed id (the pattern Phase 9 D-21 used for blocks) gives each row a stable React key. Old code paths map only key and value, so the extra field is ignored if this is ever rolled back. That is also `reversible`.
3. The column handle swaps on drop, with a drop indicator, rather than moving live. There are only two columns, and the header labels stay in place, which suits a live index-based drag badly. It is a small own component, `ColumnSwapHandle`; `OrderDragHandle` is not changed.
4. Row handles keep the house label «Изменить порядок: строка N» (OrderDragHandle prefixes «Изменить порядок: »). UI-SPEC wrote «Переставить строку N». The column handles use UI-SPEC's «Переставить столбец «…»».
</objective>
