## Critical Issues

### CR-01: Escape в многострочном `LiveCommitText` сохраняет правку вместо отмены

**File:** `components/portia-editor-live.tsx:676-677`
**Issue:** В варианте `multiline` обработчик Escape вызывает `setTyped(null)` и сразу же `event.currentTarget.blur()`. Событие blur срабатывает синхронно, внутри того же keydown. Обработчик `onBlur` взят из последнего зафиксированного рендера, в котором `typed` ещё содержит набранный текст: React применит `setTyped(null)` только после выхода из обработчика (в React 18/19 синхронные обновления сбрасываются микрозадачей). В итоге `commit(typed)` отправляет `save-qualification-rules` или `save-task-item` с текстом, от которого владелец только что отказался. План (T-26.1, «Escape отменяет правку») для правил (`CandidateRules`, `multiline: true`) и текста заданий (`CandidateTasks`, `multiline: true`) нарушен. Однострочный `span` ведёт себя правильно: он сначала возвращает `textContent = value`, и `commit` видит равенство. Тест `lib/live-edit.test.ts:1404` проверяет лишь наличие строки `event.key === "Escape"` в исходнике, поэтому дефект не ловится.
**Fix:**
```tsx
const cancelled = useRef(false);
// ...
onKeyDown={(event) => { if (event.key === "Escape") { event.preventDefault(); cancelled.current = true; setTyped(null); event.currentTarget.blur(); } }}
onBlur={() => { const skip = cancelled.current; cancelled.current = false; if (!skip && typed !== null) commit(typed); }}
```
Нужен и поведенческий тест (Playwright или jsdom): набрать текст, нажать Escape, убедиться, что POST `/api/promotion/banks` не ушёл.

### CR-02: вторая команда живого «Повышения» молча выбрасывается, а состояние показывает «сохранено»

**File:** `components/portia-promotion-editor-main.tsx:152-167` (`runCommands`), а также `:132` (`useLiveOrder`), `:172-188` (`commitText`), `:223-237` (`switchItem`, `removeItem`)
**Issue:** `runCommands` возвращает `null`, если `savingRef.current === true`, и ничего не сообщает. Последствия:
- **Две правки подряд.** Владелец правит текст вопроса и Tab-ом переходит к варианту. Пока первый `save-question` в пути, blur второго места вызывает `commitText`, и тот получает `null`. `LiveCommitText` в `finally` сбрасывает `typed`, а `useLayoutEffect` (`:659`) возвращает старый текст. Вторая правка пропадает, а когда завершится первая команда, строка состояния покажет «Вопрос обновлён.».
- **Перестановка во время сохранения.** Таймер `useLiveOrder` (450 мс) вызывает `persist`, получает `null`, и `.finally(() => setPending(null))` откатывает порядок без всякого сообщения.
- **Клик по кнопке строки.** Blur поля срабатывает раньше click по «Выключить», «×» или «Ответ…», а `postBank` синхронно ставит `busy`. Клик либо попадает в уже отключённую кнопку, либо отбрасывается `savingRef`. Подтверждённое удаление (`requestConfirm(... run: () => void run(...))`) тоже может быть отброшено после того, как пользователь нажал «Удалить вопрос».

Это потеря пользовательского ввода с ложным сообщением об успехе.
**Fix:** не отбрасывать, а ставить в очередь, или хотя бы явно отказывать:
```ts
const queue = useRef<Promise<unknown>>(Promise.resolve());
const runCommands = (payloads: Record<string, unknown>[], message: string) => {
  if (payloads.length === 0) return Promise.resolve(null);
  const next = queue.current.then(async () => { /* текущий цикл post(...) без проверки savingRef */ });
  queue.current = next.catch(() => undefined);
  return next;
};
```
Если очередь нежелательна: при занятом `savingRef` вызывать `refuse("Подождите: предыдущее изменение ещё сохраняется.")`, а `LiveCommitText` при отказе должен оставлять набранный текст (см. WR-01).

### CR-03: e2e «карточка слишком длинная для PNG» ждёт имя файла, которого в тесте нет

**File:** `tests/e2e/specs/template-builder.spec.ts:746`
**Issue:** `downloadHtml(page, builder, testInfo, "Д".repeat(110), "long.html")` ждёт `suggestedFilename()` равным `templateDownloadName("Д".repeat(110), "html")`, то есть 80 букв «Д» и `.html`. Но этот тест (`:728-751`) название вируса не вводит. `"Д".repeat(110)` вводится в *следующем* тесте (`:756`, «long unbroken text and a wide image…»). У каждого теста Playwright свой контекст, а черновик конструктора не сохраняется (по `lib/portia-template-builder.test.ts` хранилище трогает только позиция панели). Значит, реальное имя здесь `shablon-dosye.html`, и сценарий падает при каждом запуске. По 26.1-19-SUMMARY.md спека не запускалась (BLOCKED), так что ошибка не замечена. Выглядит так, будто при правке `ab5e57ee` перепутали соседние тесты.
**Fix:**
```ts
// у вируса в этом сценарии нет названия: файл сохраняет старое имя
const { html } = await downloadHtml(page, builder, testInfo, "", "long.html");
```
Если нужна проверка обрезки до 80 символов, перенесите её в тест `:753` (там название вводится) или в unit-тест `templateDownloadName`.

## Warnings

### WR-01: при отказе сервера набранный в живом режиме текст теряется, а баннер пишет «Ваш ввод сохранён»

**File:** `components/portia-editor-live.tsx:655-665`; `components/portia-promotion-editor-main.tsx:350` (`postBank`), `:270` (баннер конфликта)
**Issue:** `commit` в `finally` всегда делает `setTyped(null)` и `setRunning(false)`. После этого `useLayoutEffect` возвращает в `span` сохранённое `value`, а `textarea` показывает `value`. При 409, 400 или отсутствии сети набранный текст исчезает. В это же время `postBank` при 409 ставит `conflict`, и над поверхностью появляется баннер «Данные изменились. Ваш ввод сохранён.» с кнопкой «Оставить мой ввод». В живом режиме ввод не сохранён нигде, так что баннер вводит в заблуждение.
**Fix:** пусть `onCommit` возвращает признак успеха (`Promise<boolean>`). При неудаче `typed` и `textContent` не сбрасывать, место остаётся «грязным» до следующего blur или Escape. Баннер «Ваш ввод сохранён» в живом режиме не показывать или заменить текстом «Изменение не сохранено, текст оставлен в поле».

### WR-02: включение живого режима «Повышения» размонтирует обычные редакторы и теряет несохранённое

**File:** `components/portia-promotion-editor-main.tsx:368`
**Issue:** `live ? <PromotionLiveSurface …/> : branch === "tasks" ? <PortiaPromotionOrdinaryEditor …/> : <PortiaPromotionQualificationEditor …/>` при включении режима размонтирует обычный редактор. С ним пропадают его локальные состояния: `rulesDrafts`, `newDraft`, открытый `dialog`, `manualIds`, собранное превью набора `preview` с токеном (`portia-promotion-qualification-editor.tsx:33-44`), а у заданий `draft` и `editingId`. Предупреждения нет. В «Доступе» тот же переключатель сделан правильно: менеджер остаётся смонтированным (`portia-editor-live.tsx:985`, «so nothing typed there is lost»). Поведение двух вкладок расходится.
**Fix:** держать обычный редактор смонтированным, как в «Доступе»:
```tsx
<div hidden={live}>{branch === "tasks" ? <PortiaPromotionOrdinaryEditor …/> : <PortiaPromotionQualificationEditor …/>}</div>
{live && <PromotionLiveSurface key={branch} …/>}
```
Другой вариант: при наличии черновиков спрашивать подтверждение перед переключением.

### WR-03: кнопка «ЖИВОЙ РЕЖИМ» на ветке «Запросы» ничего не делает (владелец принял)

**File:** `components/portia-promotion-editor-main.tsx:356`, `:368`

### WR-04: кэш снимков окон `lastPreviewClone` переживает смену зрителя и показывает устаревший снимок как «сейчас»

**File:** `components/portia-desktop-taskbar.tsx:53`, `:150-173`
**Issue:**
- `lastPreviewClone` — это `Map` на уровне модуля. Её не чистят при размонтировании `PortiaDesktop` и при смене `viewerKey` (`onAccessLost`, смена учётной записи в той же вкладке). Сценарий: зритель A навёл курсор на превью окна X, после этого доступ потерян или сменился зритель. Зритель B открывает X и сворачивает его, не наводя превью. Тогда `paint()` не находит видимый источник (`display: none` у свёрнутого окна, `portia-desktop-window.tsx:188`) и показывает снимок окна, сделанный при A, с данными A (карточки досье, редактор). Это утечка содержимого между сеансами одной вкладки.
- Снимок записывается при *закрытии превью*, а не при сворачивании окна. Превью свёрнутого окна показывает то, что было при последнем наведении, возможно час назад, хотя по смыслу (OWN-06) это «то, что окно показывает сейчас».
- Записи для закрытых окон не удаляются, пока на их кнопку снова не наведут курсор (а у закрытого окна кнопки нет). Отсоединённые копии больших окон (редактор) остаются в памяти: по одной на приложение.
**Fix:** делать снимок в момент сворачивания (в `AppWindow` перед `display: none` или в обработчике minimize) и хранить его в состоянии `PortiaDesktop`, которое сбрасывается вместе с `viewerKey`. Минимально: экспортировать `clearPreviewClones()` и вызывать его в cleanup эффекта `PortiaDesktop`, при смене `viewerKey` и при закрытии окна (`lastPreviewClone.delete(app)`).

### WR-05: «Выровнять значки по сетке» допускает два ярлыка в одной клетке

**File:** `components/portia-desktop-shortcuts.tsx:263`, `:292-299`; `lib/shortcut-layout.ts:121-130`
**Issue:** `alignShortcutsToGrid` раздаёт свободные клетки так, что «nothing overlaps». Но при включённой сетке бросок мышью (`snapShortcutPosition(operation.last, …)`) и шаг Alt+стрелка (`base + sign * cells * (cell + gap)`) ставят ярлык в ближайшую клетку, не проверяя, занята ли она. Препятствиями `clampShortcutPosition` считает только помощника и кнопку форматирования, другие ярлыки в них не входят. Поэтому ярлык ложится точно поверх соседнего и полностью его закрывает; с клавиатуры это происходит за одно нажатие Alt+→. Кроме того, после snap вызывается `clampShortcutPosition`, который при попадании на препятствие сдвигает ярлык вне сетки, и режим «по сетке» молча нарушается.
**Fix:** при `grid` искать ближайшую *свободную* клетку: переиспользовать `alignShortcutsToGrid` с текущими позициями остальных ярлыков как занятыми, а при Alt+стрелке перепрыгивать занятую клетку или отказывать с объявлением через `onAnnounce`. Clamp выполнять до snap либо снапать результат clamp повторно.

### IN-06: `request.text()` читает тело целиком до проверки лимита

**File:** `app/api/promotion/banks/route.ts:98-99`
**Issue:** L1 проверяет размер по уже полностью прочитанному тексту. Регрессии здесь нет: старый код тоже читал всё. Но авторизованный проверяющий может прислать тело любого размера, ограниченное только платформой (Netlify около 6 МБ), и оно будет буферизовано.
**Fix:** перед `request.text()` отказывать по `Content-Length > BANK_BODY_LIMIT` (413), а для потоков без длины читать `request.body` с ограничением по счётчику байт.

### IN-07: Generality without instantiation — `LiveApp` «access» никто не предоставляет

**File:** `lib/live-edit.ts:15`, `:29`, `:33`
**Category:** necessity
**Issue:** В `LiveApp`, `LIVE_TABS` и `liveAppOfTab` добавлен `"access"`, но провайдера с `app: "access"` и вызова `useLiveEdit("access")` в репозитории нет (`grep` по `components/` и `lib/`). `AccessLiveTab` рисует экраны ворот без контекста, а `useLiveMode("access")` всё равно возвращает `toggle = null` через `LIVE_SEAM_TABS`. Значение участвует только в проверке «у вкладки есть живой режим». Это суждение (возможно, его ждут тесты), поэтому Info.
**Fix:** оставить решение человеку. Можно убрать `"access"` из `LiveApp` и держать признак наличия живого режима отдельно (`LIVE_SEAM_TABS`), не расширяя тип приложений контекста.
