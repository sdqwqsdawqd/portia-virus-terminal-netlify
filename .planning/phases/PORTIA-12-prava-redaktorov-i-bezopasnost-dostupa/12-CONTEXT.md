# Phase 12: Права редакторов и безопасность доступа - Context

**Gathered:** 2026-10-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Владелец в разделе «Доступ» включает и выключает каждому редактору 7 вкладок: База вирусов, Информация, Сводка, Корзина, Рекомендации, Помощник, Сотрудники. Редактор не видит закрытых вкладок. Сервер отклоняет правки закрытых разделов, даже если запрос послан в обход интерфейса. В редактор пускает только подтверждённая почта: проверка в коде работает сразу, а SQL владелец применяет сам. Путь `//host/x.png` больше не считается локальным ни в коде, ни в SQL. Без применённого SQL у всех редакторов все вкладки, и сайт работает как раньше.

Требования: SEC-01, SEC-02, CONT-09, PERM-01, PERM-02, PERM-03, PERM-04.

</domain>

<decisions>
## Implementation Decisions

### Carried forward (locked earlier, not re-asked)
- **D-00a:** Без применённого SQL нового столбца нет, у всех редакторов все вкладки. Код работает и до SQL, и после (v1.1 roadmap, STATE.md).
- **D-00b:** SQL прав и подтверждённой почты — один блок владельца в конце фазы. В нём: предварительная проверка `auth.users`, откат, `begin/commit`. Владелец сам проверяет «Confirm email» в Supabase и сам применяет SQL (SEC-02, STATE.md ⚠️ Phase 12).
- **D-00c:** Опрос контента раз в 10 с, пока вкладка браузера видна (03.2-07). Новые проверки прав опираются на этот опрос.

### Вкладки в «Доступе» (PERM-01, PERM-02)
- **D-01:** Переключатели стоят прямо в строке редактора списка «Аккаунты редакторов»: под почтой ряд из 7 чипов, по одному на вкладку. Порядок и названия как во вкладках редактора (`sectionLabels` + «Сотрудники»). Отдельного окна и таблицы нет.
- **D-02:** Нажатие на чип сразу переключает вкладку и сохраняет. В строке появляется короткая пометка «Сохранено» или ошибка. Так же сейчас работают «ВЫДАТЬ ДОСТУП» и «ОТОЗВАТЬ»: «Доступ» сохраняется отдельно от кнопки «СОХРАНИТЬ» редактора.
- **D-03:** «ВЫДАТЬ ДОСТУП» остаётся как есть, без выбора вкладок. Новая строка появляется со всеми чипами включёнными (PERM-02).
- **D-04:** До применения SQL чипы видны, все включены и не нажимаются. Под ними одна строка: «Вкладки по редакторам заработают после применения SQL».
- **D-05:** В базе хранится список **закрытых** вкладок, пустой список означает «всё открыто». Будущая новая вкладка (например, «Справочник») сама открыта всем редакторам. — **Reversibility:** costly — переход на список открытых вкладок потребует миграции данных у всех редакторов и смены SQL-функций.
- **D-06:** Кнопок «ВСЕ» и «НИЧЕГО» нет, только 7 чипов.
- **D-07:** Можно закрыть все 7 вкладок, не отзывая доступ («заморозка»).
- **D-08:** Вид чипа: открытая вкладка — цвет акцента и ✓, закрытая — серая и перечёркнутая. Состояние видно не только по цвету, у чипа есть `aria-pressed`.
- **D-09:** «Доступ» остаётся вкладкой только владельца. Переключателем он не управляется, у владельца всегда все вкладки.

### Насколько строго закрывать (PERM-04)
- **D-10:** Сервер сайта проверяет всё. `PUT /api/content` сравнивает сохранённый контент с присланным через `changedSections()`. Если изменён хоть один закрытый для редактора раздел — отказ. Маршруты `/api/employees` (PATCH/POST/DELETE) требуют вкладку «Сотрудники».
- **D-11:** В самой базе по вкладке «Сотрудники» закрыты таблицы `portia_employee_profiles` и `portia_manual_employees` (RLS). Строку контента `portia_content` база по-прежнему пускает любого редактора: триггер по разделам JSON делать не стали. Это **принятый риск**: его нужно записать в PROJECT.md (Known Limitations) и в записях ревью. Риск: редактор, знающий технику, может записать закрытый раздел контента прямо в Supabase. — **Reversibility:** reversible
- **D-12:** Сохранение с изменённым закрытым разделом отклоняется **целиком** (403 с названием раздела, например «Раздел «Сводка» для вас закрыт»). Частично ничего не записывается, черновик остаётся на экране.
- **D-13:** Удаление вируса переносит его в Корзину, и это разрешено, даже если «Корзина» закрыта. Перенос считается правкой «Базы вирусов». Менять и восстанавливать что-либо в самой Корзине редактор без этой вкладки не может. Серверная проверка должна различать эти случаи: вирус ушёл из `viruses` в `recycledViruses`/`recycleOrder`, и меняются его тексты `virus:<id>:*`.
- **D-14:** «Не видеть, что внутри» относится только к редактору: у закрытой вкладки нет кнопки, полей, оформления и черновика (PERM-03). Публичный рабочий стол показывает все разделы всем, как сейчас.

### Редактор при закрытии (PERM-03)
- **D-15:** Если владелец закрыл вкладку, у открытого редактора она пропадает примерно за 10 с: права перечитываются вместе с опросом контента. Сервер в любом случае отклонит правку (D-12).
- **D-16:** Несохранённые правки закрытого раздела возвращаются к тому, что лежит в базе, и появляется сообщение: «Владелец закрыл раздел «…», несохранённые правки в нём сброшены». Правки открытых разделов остаются, их можно сохранить.
- **D-17:** Если закрыты все 7 вкладок, значок редактора на рабочем столе остаётся. Внутри нет вкладок, только сообщение «Владелец пока не открыл вам ни одного раздела».

### Неподтверждённая почта (SEC-01, SEC-02)
- **D-18:** Проверка в коде: `getEditorAccess` не даёт доступа пользователю без `email_confirmed_at`, и до SQL, и после.
- **D-19:** Человек с неподтверждённой почтой после входа видит на странице входа: «Почта не подтверждена. Откройте письмо от Supabase и войдите снова». Редактор не открывается. Кнопки повторной отправки письма нет.
- **D-20:** SQL выдаётся двумя частями. Первая — отдельный файл-инструкция (например, `supabase/phase12_apply.sql`) с пронумерованными шагами: 1) предварительная проверка, 2) применение в `begin/commit`, 3) проверка после, 4) откат. Вторая — обновлённый `supabase/portia_setup.sql`, чтобы установку с нуля можно было запустить одним файлом.
- **D-21:** Предварительная проверка выводит владельца и каждого редактора из `portia_editors`: есть ли аккаунт и подтверждена ли почта. Если почта **владельца** не подтверждена, блок прерывается сам и ничего не применяет. Что делать с неподтверждёнными редакторами, решает владелец: пишет им или подтверждает их в панели Supabase.
- **D-22:** Исключения для владельца в SQL нет: при выключенном «Confirm email» почту владельца мог бы зарегистрировать посторонний. Именно это и закрывает SEC-02.

### `//host` (CONT-09)
- **D-23:** Локальный путь начинается с одного `/`, `//…` к локальным не относится. Это касается всех проверок в коде (`lib/portia-content-normalize.ts:83`, `lib/portia-employees.ts:523`, распознавание ссылки в `components/portia-editor.tsx:91`) и CHECK у `portia_employee_profiles.photo_url`. Ограничение добавляется как `not valid` и включается (`validate constraint`) только после проверки существующих строк. Проверку строк включить в предварительную проверку D-21.

### Задел под будущие вкладки (/gsd-explore 2026-10-26)
- **D-24:** Хранение прав сразу поддерживает два вида вкладок:
  - **обычные** — по умолчанию открыты: список закрытых, D-05. Это 7 вкладок сайта и будущий «Справочник»;
  - **доверяемые** — по умолчанию закрыты: список выданных. Первая такая вкладка — будущее «Повышение»: одобрение заявок, выдача заданий, квалификационные проверки.
  
  В фазе 12 доверяемых вкладок ещё нет. Но столбцы и SQL-функции устроены так, чтобы «Повышение» потом добавлялось без нового SQL владельца, только строкой в коде. — **Reversibility:** costly — если сделать только список закрытых, «Повышение» по умолчанию окажется открыто всем, и понадобится новый SQL и миграция.
- **D-25:** Чип «Повышение» в «Доступе» появится вместе с приложением. Выглядит как остальные чипы (D-08), но новая строка редактора получает его выключенным. «Доступ» (выдача и отзыв редакторов) по-прежнему только у владельца, и передать его нельзя.

### Claude's Discretion
- Имена столбца и функции. Например: `portia_editors.closed_tabs text[] not null default '{}'` с ограничением на известные идентификаторы и `portia_can_edit_tab(tab text)`. У владельца нужно право UPDATE на этот столбец: сейчас на `portia_editors` выданы только select/insert/delete.
- Как код узнаёт, что SQL ещё не применён: например, по ошибке «нет столбца» при чтении. В этом случае считается, что всё открыто, а владельцу возвращается флаг для D-04.
- Загрузка файлов (`/api/uploads`) разрешена, если у редактора открыта хотя бы одна вкладка.
- Если редактор стоял на закрытой вкладке, он переходит на первую открытую. Ctrl+Z не возвращает правки закрытого раздела.
- Нужен ли идентификатор вкладки «employees» в общем списке разделов или он идёт отдельно от `EditorSection`.
- Проверять ли заодно `/\host` (браузер читает его как `//host`). Решает исследователь, но строже не хуже.

<code_context>
## Existing Code Insights

### Reusable Assets
- `changedSections(baseline, draft)`: готовое сравнение разделов. Сервер сравнивает строку из базы с присланным контентом и получает список изменённых разделов.
- `getEditorAccess`: сюда добавляются `email_confirmed_at` и список закрытых вкладок, чтобы все маршруты получили их разом.
- Список «Аккаунты редакторов» в `components/portia-editor.tsx`: строки уже есть, чипы добавляются в каждую.
- Опрос контента раз в 10 с: к нему подключается перечитывание прав (D-15).

### Established Patterns
- Правила доступа живут в Supabase (`portia_can_edit`/`portia_is_owner`), сайт их только вызывает. Новая проверка вкладки следует тому же: SQL-функция плюс вызов из `getEditorAccess`.
- `portia_setup.sql` можно запускать повторно: `create or replace`, `if not exists`, `drop policy if exists`.
- Сообщения пользователю на русском, ошибки API — JSON `{ error }` с кодом 403/400/500.

### Integration Points
- Вкладки редактора: `editorSections` + `employees` + `access` (только владелец).
- Весь контент лежит одной строкой `portia_content` с `id = 'main'`. Тексты разделов хранятся в `formattedText` с префиксами ключей (`virus:`, `info:`, `broadcast:`, `recycle:`, `search:`, `assistant:`).

</code_context>

## Specific Ideas
